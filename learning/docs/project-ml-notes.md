# 边做边学：项目里的机器学习（2026-10-30起）

## 2026-11-27：数据能解析，还要证明消费者用对了

解析成功只说明工程读取成立。若复盘代码仍用旧地图、营地和机制，新补丁的数据不能直接进入同一分析。新输入用精确补丁门禁，并把生产者、消费者和知识/地图分开记录指纹；旧字节完全没改，也可能因为消费规则变了而得到不同结论。

按整文件记录指纹会把缓存校验改动也计入。此次两组 Gem 指纹不同，Git 溯源证明解析/序列化代码段一致，但旧 raw 原文件缺失，因此只能解释差异，不能认证整个旧包。严格拒绝默认仍保留，当前工作直接用新验收包。

裁掉赛后状态时，观察终点必须同步改成比赛时长，否则“随后20秒”会把赛后当成仍有观察。赛前可见性事件又不能一刀切掉：最后一次显隐变化可能在负秒，先应用初始化，再输出游戏内视野，才能保留0秒时已知的状态。输入完整性、游戏时间边界和事前可知性是三种不同的检查。

## 2026-11-27：省存储时怎么证明没有丢数据

首先盘点重复副本。五场试采 3.18 GiB 中，94.9% 在工作目录；先取消重复的 raw/prepared/input/cleaned，比降低逐秒采样率更直接。新流程保留压缩原 demo，raw/normalized 直接写 gzip，state/extras 边提取边压缩。gzip 固定时间戳，记录压缩与解压后两种摘要；不改变浮点精度或游戏内采样密度。

证明有三层：原字节 SHA 一致证明无损归档；新旧逐秒行对账证明解析重构没有改变对应通道；比赛 ID、结束、覆盖和字段质量证明产物达到工程要求。三者仍不证明模型有效。normalized 的来源路径和摘要会随新存储改变，必须列出这些差异，不能把语义一致写成整文件逐字节相同。

真实录像暴露了合成测试未覆盖的问题：Gem 输出树中仍有字符串枚举，普通 JSON 会转成字符串，严格写入器却会拒绝。修复在树内转换成 JSON 基本类型，避免先生成巨大的 JSON 字符串再解析。64 KiB 缓冲减少小 token 调用 gzip 的次数；这个局部基准的提速不能当作整局解析提速。

复用缓存也要验证来源和质量。文件存在、摘要正确，只说明“当前这些字节没有变化”；还要确认补丁、真实比赛身份、生产者，以及每秒覆盖确实符合当前要求。失败日志和旧 attempt 保留，才能区分解析失败、质量待复核和来源已变。列式存储适合以后按列扫描特征表，当前采用已有 gzip 先解决重复与大字符串问题；详见[实现与实测](../../docs/replay-pipeline-v2.md)。
