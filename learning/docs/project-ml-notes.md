# 边做边学：项目里的机器学习（2026-10-30起）

## 2026-11-26：完成数、完整性与可观测性

- **金额对账和机制解释是两层问题**：一例敌法师并非击杀者，却在队友击杀时增加 neutral 计数和钱包；4 金确实到账，原始 GOLD 没有该玩家记录，附近另一次 5 金有完整日志作正对照。此前堆过野不等于已证明这笔钱来自堆野。账目可以定位，同时把分配机制保留未知；不能由金额比例反推引擎规则。
- **单位名字不等于金币分类**：英雄所属的巨魔骷髅可进入 creep 分类。要检查当时阵营、实体身份、owner handle 与 PlayerResource 的对应，不凭阵容猜主人，也不把多个同 tick 死亡的聚合差额拆成单只赏金。
- **同一个 tick 不保证只有一个状态**：解析器可能在同一录像 tick 多次回调，中间有实体更新。独立重放需要保持回调顺序；事前采样固定每秒首个回调，不能被同 tick 或同秒后续值覆盖。
- **名称索引也有所属表**：具体 NPC 单位名由 `m_iUnitNameStringTableIndex` 查 `UnitNames`；`EntityNames` 可能只是 `npc_dota_creep_neutral`。把同一索引查到另一张表，会读出完全不同的技能或物品名称。

- **状态文件不是进程存活证明**：异常中断可能来不及写结束状态。恢复前查实际进程，保存旧锁和证据，再验证已有输出后续跑，不能看到 running 就一直等，也不能直接抢锁。
- **摘要正确不等于数据正确**：逐文件校验和可以检出字节损坏，但漏行后重算校验和仍可能通过。审计还要对照固定机会全集，从保存端点和事件重算每个窗口，区分提取完成、数值对平与语义核查完成。
- **部分结果要有固定快照**：批次仍在写时，审计先固定已发布文件列表，后来完成的比赛留待下一份报告；否则不同计数可能来自不同人口。
- **可见的数量不是总存量**：己方没看到中立单位不等于营地空了。实际 NPC 可见位图只告诉我们单位是否可见，不能证明整个营地区域被完整观察；同 tick 包前状态也不能拼接包末才更新的可见性。

## 2026-11-25：真实收益、未知与长批次复现

- **单位控制者不是金币归属者**：控制器重建让解析器缓存把两个玩家指向同一队友，若沿用它会把英雄属性和另一人的经济拼成一行。修复从游戏的 PlayerResource 名册、选定英雄、阵营槽位确定归属，并验证实体序号。数值看起来合理不代表行身份正确。
- **两个来源不相等，要查各自覆盖范围**：实体累计有小额收入，但相同 tick 的 GOLD 通道可能没有事件。已核的 13 个差额格都有具体证据，不能为了对平删金额或补造流水，也不能由少数样本发明“引擎统一过滤阈值”。creep 字段还含敌方召唤物，字段名不等于纯兵线的研究定义。
- **扩大验证会推翻小跑的乐观印象**：前 16 场全部对平，扩大到 53 场发现收入覆盖差异和身份错误。先保留原结果、找到原因、换新版本重提，再检查影响范围；不能把受影响的一段外推成整批失效，也不能只修报错而忽略旧特征可能混合身份。

- 现金余额差不能替代收入：购物会减少现金却不改变刷钱所得。分别读取小兵和野怪累计实收，并用逐笔事件交叉核对，才知道目标量是否测对。新旧目标不同，误差不能直接比较。
- 零和未知要分开：完整观察没有收入是零；没读到端点或比赛提前结束是未知。只留下成功刷到钱的转野，会系统性丢掉空营地、死亡与失败路线，制造选择偏差。
- 动作、后果和事前条件是三个对象：未来走位可帮助识别实际动作，未来金币可作结果；它们都不是决策时的输入。仅有营地坐标，仍不知道当时有没有野、看不看得到、能否走通。
- 动态参照物会影响规则：英雄离决策时的固定兵线前沿越来越远，可能因为兵线也在前进。本轮 567 段诊断例子支持研究这个问题，但不能代替人工真值或直接改标签。
- 可恢复不只是“文件存在就跳过”：长批次需要绑定机会全集、录像字节、解析器及代码，保存逐场摘要，复用前再次核验；否则断点前后可能悄悄混用不同定义。[接口与证据](../../docs/b5-farm-income-batch.md)
