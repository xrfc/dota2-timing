## M2 出装时间预测：第一次真实训练

**任务形式**：把“几分钟做出狂战斧”转成5个二分类问题（10/15/20/25/30分钟前是否做出）。这是处理“时间到事件”问题的最简单做法；更正规的方法叫**生存分析**（survival analysis），以后可以学。

**基线（baseline）**：不看阵容，直接用训练集的平均概率。任何模型都要先打败它才有意义。

**逻辑回归**：`p = 1 / (1 + e^-(w·x + b))`。x是阵容的one-hot向量（某英雄在敌方→对应位置为1），w是每个英雄的权重，b是截距。训练就是找让训练数据“最不意外”的w、b（最大似然）。

**正则化（L2，参数C）**：在目标里加`‖w‖²`惩罚，防止权重过大。C越小惩罚越强。

**评估指标**：
- Brier分数 = 预测概率与0/1结果之差的平方平均，越低越好；
- 对数损失（log loss）对“很自信却错了”惩罚更重；
- **bootstrap置信区间**：把验证集按比赛重复有放回抽样1000次，看“模型比基线好多少”的波动范围。区间含0就不能说模型更好。

**冻结协议**：指标、基线、展示规则在训练前写死。否则人会不自觉地“调到验证集看起来好”，这叫**对验证集过拟合**，也是论文结果复现不了的常见原因。

**这次的结果——过拟合的典型样子**：
- 约250个特征、巫医只有约160个样本：每个英雄只出现几次，模型把巧合当规律，在没见过的验证集上反而更差。
- 神谕者35项里有3项“显著更好”，但验证只有15人：做很多次检验，总会有几次靠运气通过，这叫**多重比较问题**。

**可能的改进（下一步要学的概念）**：
1. **交叉验证选超参数**：在训练集内部轮流留一部分做验证，选出合适的C，全程不碰正式验证集。
2. **特征工程/降维**：把127个英雄压成几类属性（控制多、物理爆发、魔法爆发…），参数少了，样本才够用。
3. **共享参数/层级模型**：让四个英雄共享“敌方有控制→出BKB”这类规律，而不是各学各的。这正是以后学深度学习时“嵌入（embedding）”要解决的问题。

动手：打开`reports/m2-item-timing-2026-10-30-v1/results.json`，找主宰`bfury` 15分钟那一行，对比`brier_baseline`和`brier_model`，再看`calibration_model`里每个概率区间的预测值与实际比例差多少。

### M2修订2：交叉验证与正则化（第二次尝试）

**做了什么**：只用敌方英雄、合并少见英雄（特征从约250降到约105），并在训练集内部用**5折交叉验证**为每个格子从7个C里选一个。

**交叉验证怎么工作**：把训练集按比赛分成5份，轮流用4份训练、1份打分，5次平均。分组（同一场不拆开）防止泄漏；分层保证每份正负例比例相近。全程不碰正式验证集。

**结果怎么读**：80格里35格选了最小的C=0.001（最强正则）——相当于把权重压到接近0，模型退回“只看平均率”。这不是失败，而是交叉验证在诚实地说“这里没有可学的信号”。过拟合消失了（修订1里25格显著更差，修订2只剩1格）。

**偏差–方差权衡**：修订1权重自由（方差大，记住了噪声）；修订2强正则（偏差大一点，但稳定）。数据少时，宁可简单。

**唯一信号——主宰蝴蝶**：敌方有魔法爆发/控制英雄（天怒、斧王、军团）时更晚出蝴蝶，敌方是物理核心（虚空、斯温、敌法）时更早。看**系数**就能解释模型，这是线性模型相对深度模型的优势（可解释性）。但在35+次比较里找到1个，仍要在新数据（M4）上复核才算数。

**一个流程教训**：展示规则只问“区间是否>0”，没要求最小改善量，于是改善0.0002的格子也“通过”。好的预注册协议要同时规定**统计显著**和**实际有意义的效果量**。

动手：在`reports/m2-item-timing-2026-10-30-r2/model.json`里找`8:1|butterfly|30`，看`cv_brier`里不同C的交叉验证分数，再看`coef`前104个（对应`vocab.heroes`顺序）哪些最大、最小。

### M2-T5 把模型放进页面：推理服务

**做了什么**：本地服务读取训练好的系数（`model.json`），收到“我的英雄＋敌方阵容”后现场算概率，页面画成热力表。这一步叫**推理（inference）/模型服务（serving）**：训练只做一次，推理每次查询都做。

**工程要点**：
- 服务启动时核对模型文件哈希，确保页面用的正是评估过的那个模型（模型版本管理）。
- 输入严格校验（未知英雄、重复、填自己都拒绝），这是生产环境防“垃圾进垃圾出”的基本功。
- 训练和推理用**同一个**`features`函数生成输入，避免“训练–服务不一致”（training-serving skew），这是线上模型最常见的隐形bug之一。
- 展示要诚实：模型与平均差不到1个百分点的格子，不标“阵容调整”，否则用户会以为模型在起作用。

动手：启动服务后访问`http://127.0.0.1:8780/api/item-timing?hero=8&position=1&radiant=1&enemies=101,2,104,5,67`，对比把天怒法师(101)换成虚空假面(41)后蝴蝶30分钟的概率怎么变。

### U13 问题重构：领域知识比模型更重要

**发生了什么**：用户看了页面说“出装时间应该取决于线上表现，不是阵容”。验证后：阵容对狂战斧时间的解释力≈0，自己10分钟经济R²=0.61。

**学到的概念**：
- **问题定义（problem framing）先于模型**：M2花力气证明的“阵容预测时间”从一开始就是弱问题。好的问题是“输入里确实有足够信息决定输出”。
- **R²（决定系数）**：线性回归能解释的方差比例。0.61表示10分钟经济一项就能解释狂战斧时间六成的差异。
- **机械关系 vs 可用信号**：经济决定出装时间几乎是定义上的（钱够才能买），所以它不适合“赛前预测”（赛前不知道经济），但很适合“复盘对照”（赛后知道你的经济，看你转化得快不快）。同一个关系放在不同时点，用途完全不同——这又回到M1的“何时可知”。
- **负面结果也有价值**：M2的失败把“阵容影响什么”从“时间”收窄到“选择”，直接定义了M2b。

动手：在`reports/m1-match-table-2026-10-30-v1`里，按`lh_10`分组算主宰狂战斧首次购买时间中位数，复现“每多10刀约早1分钟”。

### M2b-T0 参考数据（reference data）

**做了什么**：把官方装备列表和社区装备常量下载到本地，拼成一张“装备登记表”，记录来源URL、下载时间和哈希。

**为什么重要**：机器学习项目除了训练数据，还依赖大量“参考数据”（名称、分类、合成关系）。它们一旦靠手写，就会悄悄出错——这次就发现手写的“灵魂之戒”其实应是“魂之灵瓮”。参考数据也要像训练数据一样：有来源、有版本、有测试（例如测试“精之灵器的配件是影之灵龛+锁子甲+法师帽”）。

**对建模的影响**：针对装候选原来靠手写排除名单，漏掉了相位鞋、散华、漩涡、净魂之刃；改用登记表的“是否合成装”字段后，筛选规则可复现、可解释。
