# 学习驱动的开发流程

## 工程入口更新 — 2026-10-17

当前职责和专项检查见[模块维护指南](../../docs/modular-maintenance.md)。适配、任务/特征、拟合、制品和推理可分别学习验证；合成通过不等于泛化效果。
下方为历史学习循环，提交/推送必须另有明确授权，不能因完成练习自动发布。

更新：2026-10-03；运行代码基线 v0.3。适用于已掌握机器学习基本原理、通过项目学习数据工程与完整交付的人。

当前优先级是来源、清洗、时间对齐、样本构造和预处理。任务状态统一记录在[roadmap](roadmap.md) 的 L01–L12；本文说明如何执行。下面提出的模块、质量字段、派生样本与验收机制均是计划，不是现有 CLI 已实现的功能。

## 1. 一次迭代要交付什么

每个小任务留下三类证据：

| 证据 | 内容 | 示例 |
|---|---|---|
| 工程产物 | 可调用函数、协议、检查结果或文档 | 按 cutoff 选择最近历史观测的纯函数 |
| 验收记录 | 正例、负例、实际结果与适用范围 | 600 秒时不得选中 602 秒的位置；缺历史值返回缺失 |
| 学习结论 | 为什么这样设计、失败假设、剩余问题 | 为什么双向插值会泄漏未来，观测年龄为何应随值保存 |

先写预期行为，再实现最小改动。学习笔记可以解释原理，但不能替代可重复的验收结果。没有真实回放时先做 synthetic 的接口与边界验证，并保留真实语义验收为待办。

## 2. 开发循环

1. **选任务。** 从 roadmap 选择一个依赖已满足的 L 任务；同一时间只推进一个主要学习问题。大任务拆为一页契约、一个纯函数、一组边界验证等小改动。
2. **写任务卡。** 复制[任务记录模板](../templates/task-record.md)，写目标、范围、依赖、输入输出、验收、兼容和回退；引用相关 D/V/E/ML 编号。
3. **固定输入。** 记录 Git 提交、依赖环境、数据集/原始文件哈希和规则版本。使用专门的开发样本，不通过查看最终测试结果来选清洗阈值或特征。
4. **先验证假设。** 用能手工计算的小例子说明规则；真实语义使用[数据审计模板](../templates/data-audit.md)对照。字段未知时排除或阻塞，不能补造数值。
5. **做最小实现。** 确定性变换尽量写成无隐式全局状态的函数；文件读取、发布、CLI 接入单独处理。先让一条样本可解释，再扩大批次。
6. **验证实际风险。** 对时间边界、缺失、身份和发布行为写有意义的正反例；训练前代码尤其检查未来数据和留出集是否影响过去特征/拟合产物。
7. **审阅差异并提交。** 说明具体问题、结果、证据和限制；只提交本任务相关改动，保留现有快照与兼容策略。通过检查后同步开发分支。
8. **更新状态与复盘。** 仅在验收满足时关闭 L 任务，按实际范围更新旧任务子项。记录一个学到的机制、一个失败案例和下一步假设。

建议任务记录放在未来建立的 `learning/records/<任务ID>-<主题>.md`，只提交适合公开的设计和摘要。学习核验用的真实回放、完整玩家记录、大型输出放在 `learning/output/` 等被忽略目录，摘要用 ID/哈希引用；自定义数据路径需检查忽略规则。当前仓库提供模板，尚未创建这些任务的实际验收记录。

## 3. 环境与分支

建议本机 CPU 开始。Python 3.11/3.12，Git 可用；模型训练和 GPU 均不属于本阶段。

新克隆示例，当前功能所在分支：

```bash
git clone --branch feat/coach-workflow-infrastructure https://github.com/xrfc/dota2-item-timing.git
cd dota2-item-timing
python scripts/bootstrap.py --dev
python coach.py --workspace learning/output/workspace demo
python coach.py --workspace learning/output/workspace doctor
```

已有检出先检查 `git status`、当前分支与未提交内容，保存已有工作后再切换/更新；不要在混合改动上执行 reset/clean。进行实际回放解析时安装 `python scripts/bootstrap.py --replay --dev`，并使用独立真实工作区。具体导入命令见[教练工作流](../../docs/coach-workflow.md)。

在干净、已同步的功能分支上，为一个小任务创建工作分支，例如：

```bash
git switch -c feat/l05-causal-alignment
```

这是将来执行 L05 的分支命名示例，不表示 L05 已开始或已实现。若任务之间存在依赖，后续分支基于已验收代码；记录实际基线 SHA，而不依赖分支名推断版本。

## 4. 数据处理的边界与接口规划

| 层 | 输入 → 输出 | 约束 | 现有代码/未来位置 |
|---|---|---|---|
| 解析与标准化 | demo → raw、规范 JSON | 保留证据，统一字段语义，不破坏原始文件 | 已有 sources/gem_replay.py、gem_observations.py |
| 校验与质量 | 规范数据 → 警告、任务资格、理由 | 非法/稀有/未知分开；导入成功不等于研究合格 | 已有 workflow/validation.py 基础检查；质量扩展待实现 |
| 时间对齐 | 多条自身时序 + cutoff → 历史状态 | 向后匹配、字段级最大年龄、缺失 mask；不使用未来插值 | 计划中的数据准备模块 |
| 样本与特征 | 固定比赛 split → sample_id、X、元数据 | 仅使用所选槽位和 cutoff 之前的数据 | 计划中的 samples/features 模块 |
| 标签 | 独立未来观察窗口 → y、有效性、引用 | 观察不足与无事件分开，未来值不回流到 X | 计划中的 labels 模块 |
| 数值预处理 | train 样本 → 拟合产物；各 split → 变换结果 | fit 只用 train，transform 共用保存产物 | 计划中的 preprocessing 模块 |
| 派生快照 | 样本、规则、拟合产物 → 清单与哈希 | 保留源 dataset_id 与原 split，不覆盖整场快照 | 计划中的样本发布层 |

学习练习模块逐步建立于 `learning/exercises/`，具体命名随接口设计确定，不预先生成空模块。经独立工程任务审阅和验收后，确需用于正式管线的能力再迁入工程包；学习脚本和笔记始终留在 learning/。后续模型适配器消费这些接口，特征变换不在 train.py/predict.py 各写一套。

现有 `train` 读取的是 `coach-dataset/1` 整场快照。派生样本没有现成 Schema/CLI，不能把规划字段直接塞进现有 Pydantic 契约；L10 需要设计新版本清单及适配器如何引用它，保留旧入口兼容。

## 5. 必须讨论清楚的规则

### 缺失、清洗与质量

- 赛前购买允许负时间；位置/经济的有效时间按其独立契约检查，不能统一把全部负数删除。
- 同一装备重复购买通常是合法事件；同一比赛重复来源应按身份去重。二者不能使用同一条去重规则。
- 金币下降、XP 变化、传送导致坐标突变先核对游戏语义，不能只凭统计离群删除。7.41f 验收发现 xp_progress 并未呈现上游文档所述的升级重置，学习记录应保留该反证，不能把文档当成真值。
- 零值、无事件、缺日志、失效/过旧观测使用不同状态。短缺口是否沿用旧值、允许多旧，必须按字段配置并保留来源与 age。
- 覆盖率需定义区间、分母和有效观测规则；高采样行数不等于高时间覆盖率。所有过滤保留原因及前后计数。
- 质量信息如果依赖整局结果，可以用于离线标签资格审计，但不能作为历史输入特征；同时报告这种样本选择可能造成的偏差。

### 时间、标签与划分

- 明确输入窗口、cutoff 是否包含边界，以及未来标签窗口。示例 `[t-W,t]` 与 `(t,t+H]` 需要落实到边界测试。
- 观察到真实结束、观察被截断、通道缺失是不同情况；定义各自是否产生有效标签。未观察满未来窗口不得默认为无购买。
- 在人工核验中看过的比赛标为开发/核验数据；若它已经属于最终测试集，应明确撤销该测试用途并重新保留未见数据。
- 固定比赛划分后，只在 train 做用于选模型/阈值的数据探索与统计拟合；验证集按预先声明用途选择方案，测试集不参与选择。全体数据的格式/完整性校验可以执行，规则需预先定义并记录。
- 词表、均值/方差、中位数填补等拟合参数保存为产物；处理未知类别、零方差和整列缺失；不能在预测时重新拟合。

## 6. 验收矩阵

下表是待实现任务的验收要求，不代表当前测试已覆盖。

| 场景 | 预期结果 | 任务 |
|---|---|---|
| 修改/删除原始证据或引用越界 | 检出变化，不伪造正常结果 | L02 |
| 空日志、日志缺失、完整窗口内无事件 | 状态与资格可区分，分母可解释 | L04/L08 |
| 决策 600 秒，观测为 598 和 606 秒 | 只可选择 598；超过最大年龄则标缺失 | L05 |
| 长缺口、暂停、同时间戳冲突 | 有预先声明的确定规则与审计记录 | L03/L05 |
| 重复封装、同场多个玩家 | 不扩大独立比赛数，不跨 split | L06 |
| 在现有观测中改变 cutoff 之后的值 | 固定配置下该时刻 X 不变；y 可以变化 | L07/L11 |
| 比赛不足以覆盖未来窗口 | 按契约记录观察不足，不标成完整窗口无事件 | L08 |
| 只改变验证/测试数据 | 固定超参数与配置下 train 拟合产物不变 | L09/L11 |
| 未知装备类别、全缺失列、零方差 | 明确编码/拒绝行为，没有隐式重拟合或 NaN 扩散 | L09 |
| 保存、加载、搬迁派生产物 | 同输入变换一致，指纹可复验 | L09/L10/L12 |
| 中途失败、超时、发布前后中断 | 旧产物可读，失败状态保留，可按记录恢复 | L12 |

人工抽样不能只挑干净样本，应覆盖纳入、排除、缺失、边界和未知；记录抽样方法、种子、数量和未覆盖范围。窗口级检查与比赛级统计都要保留。

不变性检查针对固定样本时刻的特征数值/历史观测选择，以及固定配置下拟合出的统计参数；不要求包含全文件哈希的样本清单或产物 ID 保持不变。修改未来数据可能改变标签及其有效性；修改留出集可能改变源数据集身份，但不能改变 train 拟合参数。

## 7. 检查、提交与完成定义

实现阶段先跑受影响的有意义的测试，再执行项目要求的检查。仓库根目录：

```bash
.venv/bin/python -m ruff check .
.venv/bin/python -m ruff format --check .
.venv/bin/python -m pytest -q
python coach.py --workspace learning/output/workspace demo
python coach.py --workspace learning/output/workspace doctor
```

Windows 使用 `.venv/Scripts/python.exe`。纯计划/文字修改核对链接、任务依赖、现有命令及“已实现/待实现”边界，不需要增加代码测试；不要把未运行的真实回放或新接口测试写成通过。更完整要求见[验证与交付](../../docs/validation-and-delivery.md)。

提交前检查 `git diff` 与 `git status`，逐文件选择本任务改动。PR/提交说明包括：具体触发场景、结果、正反例证据、数据/Schema 兼容、已知限制和关联任务 ID。CI 通过后仍需确认真实语义验收是否满足；不能据此自动关闭 L03。

任务关闭需要代码/文档产物、实际验收记录、版本/回退说明和学习复盘。把链接补回 roadmap，更新[项目状态](../../docs/project-status.md)的实际能力及[变更记录](../../CHANGELOG.md)。可视化学习工具与模板帮助理解和记录，但不能作为任务已完成的证据。未执行的真实核验、清洗和预处理任务继续保留待办。
