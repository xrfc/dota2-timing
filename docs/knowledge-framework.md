# 机制知识框架（U26，2026-10-31；U27扩为完整版）

> **U27（2026-10-31）**：范围由“M2b的15件针对装”扩为**全英雄（含A杖/魔晶）＋全部可购买装备**，作为新里程碑MK（计划§4），中立物品与天赋以后再加。下文§4“只覆盖15件”已被替代；三层设计不变。词表与五个枚举已确认；MK-T3接口与复核说明见[机制事实](mechanics-facts.md)，当前进度以计划§7为准。

## 1. 为什么要建

英雄特性v1（U23）从技能描述文字直接跳到“某英雄有某特性”的人工判断，中间没有结构化的机制事实。用户抽查发现两类错误：

- 证据技能写错：朗戈“高机动”引用了灵呱一闪（给队友降蓝耗），实际相关的是动人之舐（把目标拉回一小段距离＋弱驱散）。
- 机制判断错：官方数据自带`dispellable`字段，v1未使用；按该字段，守护天使、虚妄之诺、折光均为**不可驱散**，却被标为“依赖可驱散保命效果”。

框架把“依据”显式写出来：用户审规则而非逐条审标注，规则对了，127位英雄的结论随之正确；补丁更新时重算即可。

## 2. 三层结构

| 层 | 内容 | 谁定 | 位置 | 状态 |
|---|---|---|---|---|
| 1 事实层 | 官方原始枚举的含义，每个取值附已知技能作核对例子 | 数据自带；含义由用户确认 | `knowledge/mechanics/enums-v1.json`，`dota_items.data.mechanics` | 草稿，待确认 |
| 2 机制规则层 | 每件针对装克制什么机制，写成可执行规则；引用第1层字段与装备官方说明 | 用户定，助手起草（即Q10） | `knowledge/mechanics/rules-v1.json`，`dota_items.data.mechanics_interactions` | 第1版（U70） |
| 3 推导层 | 英雄特性、触发条件，由规则自动算出，每条附证据链；人工改动须写理由 | 自动；用户抽查 | 待建（M2b-T6e，hero-traits v2） | — |

依赖方向：3→2→1→官方快照。第1层不含判断；第2层不直接读文字描述做判断（可引用作证据）；第3层不手填结论（例外须登记理由）。

## 3. 第1层当前内容（v1草稿）

解码字段：`dispellable`（0无可驱散效果/1仅强驱散/2弱驱散可驱散/3不可驱散）、`target_team`（无/友/敌/双方/自定义）、`damage`（无/物理/魔法/纯粹）、`type`（普通/大招）、`immunity`（U28补充：0不涉及/1对友方生效/2对减益免疫友方不生效/3穿透减益免疫/4不穿透/5对友穿透对敌不穿透）。

- 依据：Valve引擎枚举定义顺序推断，并用已知技能逐值核对（例：薄葬、回光返照、决斗→3；妖术、沟壑→1；风行、无光之盾→2）。
- 校验：`load_enums`要求每个例子技能存在且取值一致，且登记表中出现的每个取值都有解释；补丁带来新取值会直接报错，不会被默默猜测。
- 暂不解码：`behavior`其余位、`target_type`。（`immunity`原暂不解码，U28按用户对减益免疫的说明补充解码。）
- 局限：快照未核对补丁（`patch_verified=false`）；`confirmed`全部为false，等用户确认（五个字段全部由用户确认，U30；MK-T2完成）。

装备侧已知事实（第2层将引用）：否决坠饰主动“Nullify”为**弱驱散**（OpenDota dotaconstants物品说明`Dispel Type: Basic Dispel`，`knowledge/items/sources/dotaconstants-items.json`）。

## 4. 复用与不做

- 复用`knowledge/recommendation/7.41f-v1/knowledge.json`的事实格式（来源指针＋原文引用＋中文摘要＋条件），第2层沿用。
- 范围只覆盖主宰6件针对装与辅助9件（U15、U21）；不做全英雄全装备通用知识库（用户未选C）。
- 不改冻结产物：hero-traits v1、交叉检查报告v1保持原样；v2另建。

## 5. 机制词表（MK-T1，草稿待用户拍板）

`knowledge/mechanics/vocabulary-v1.json`：45项机制（U28新增`mana_gain`；U29新增`status_resistance`、`slow_resistance`）、9类（控制、防御/保命、状态与驱散、生命/法力、单位、位移、伤害、攻击修正、施法方式）。每项有定义与判定依据：

- `enum:X`：已解码的官方枚举（如`effect_dispellability`用`dispellable`，伤害类型用`damage`）；
- `field:X`：技能原始字段（如法力消耗数值、`behavior`位掩码）；
- `item_attr:X`：装备属性字段（OpenDota dotaconstants `attrib`，如散夜对剑的`status_resistance`），U29新增；
- `official_text`：官方说明中的明确表述（如“施加破坏效果”“破坏会使……失效”）；
- `manual`：人工判断（目前没有项只靠人工）。

`load_vocabulary`校验编号唯一、类别存在、依据类型合法（`enum`必须是已解码字段）。

与v1的关系：v1的9个特性拆成更细、更客观的机制，例如“依赖可驱散保命效果”＝防御类机制（免死、护盾等）×`effect_dispellability`；“高机动”拆为`self_mobility`与`displace_other`（朗戈动人之舐属于后者）；新增破坏、隐身/真视、沉默、减益免疫/穿透、持续施法等。

用户回答（U28，2026-11-01）：

1. 缺漏：暂未发现。
2. 闪避与致盲：**分开**（U30）。此前——用户问致盲是什么效果，助手已解释（致盲＝让敌人的攻击落空，例：修补匠激光、力丸烟幕、光之守卫致盲之光）。用户随后指出金箍棒好像解决不了致盲：官方说明里金箍棒/标枪/血棘只写“穿透闪避”，无装备说明提到致盲，与v1数据（致盲对金箍棒−3%）一致。克制关系不同，助手建议分开，等用户决定。
3. 受破坏影响＝英雄的**关键被动**（如敌法师法力损毁、潮汐猎人海妖外壳）。官方说明不总注明破坏，海妖外壳的`behavior`也不含被动位，因此“关键被动”由助手标注、用户抽查。
4. 法力依赖＝高蓝耗**且**缺少自身回蓝手段（新增`mana_gain`；莱恩有法力吸取，所以依赖低）。门槛在MK-T4/T5定。
5. 减益免疫：只有穿透减益免疫的效果才生效（如碎颅锤重击可眩晕开黑皇杖的单位）；据此解码`immunity`枚举，`pierces_debuff_immunity`技能看`immunity=3`。

## U31：指向方式与物品响应分开

用户确认三项独立记录：能否主动选择敌方单位、是否触发林肯格挡、是否触发莲花反弹。`vocabulary-v2.json`只修订单体指向定义，允许兼容友方目标；具体交互逐项核对，缺证据为未知。原词表/抽取v1保持不变，语义复核引用v2。例子与来源见[复核说明](mechanics-review.md)，用户决定见[U31](decisions/2026-11-01-targeting-interactions.md)。

## 6. 第2版证据（MK-T3，2026-11-01）

依据Claude第1轮复核（`knowledge/mechanics/reviews/claude-round-001/`）与用户回答U33、U35，新建v2，v1冻结包不改：

- **词表v3**：召唤物包括不可控单位与夺取控制；反伤包括固定值反击；减伤包括延迟伤害；“受破坏影响”改为事实层的“可被破坏”，英雄多怕破坏另见`break-vulnerable-heroes-v1.json`（推导层）；闪避、减伤、治疗削减、吸血、真视增加装备属性字段证据。
- **抽取规则v2**：匹配前去掉英雄名；跳过“被眩晕时……”“可躲避眩晕”这类状态描述和“能命中隐身单位”这类交互说明；先减去“减速抗性”“在目标间跳跃”“标记为反射伤害”等形近短语；补上“lower movement”“prevents … from attacking”“反击”“take control”“延迟伤害”等说法。
- **用第1轮判断衡量规则**：v2去掉了v1的94组（第1轮全部判为排除），**没有去掉任何第1轮接受的组**；新增14组（斯嘉蒂之眼减速与治疗削减、天堂之戟缴械、希瓦光环、冰晶爆轰禁疗、蛙力千钧减速、斧王·反击螺旋、勇气之霎、虚妄之诺减伤、陈·神圣劝化、魅惑、支配/统御头盔、感染），Claude已逐组复核为接受（`claude-round-002/new-in-v2.jsonl`）。第1轮排除的组仍有192组被v2保留，规则无法区分，靠人工判断。
- **局限**：第1轮判断主要是Claude的（部分经用户U33/U35改判），用它衡量规则只能说明“与这轮人工判断一致”，不等于游戏真值；`patch_verified=false`。

## 7. 第3版证据：去掉已失效的升级文字（2026-11-01）

用户U5抽查发现殁境神蚀者·奥术天球A杖、琼英碧灵越界魔晶的说明与当前游戏不符。原因：Valve datafeed对技能保留`scepter_loc`/`shard_loc`文字，即使该技能当前没有这项升级（`ability_has_scepter`/`ability_has_shard`为false）；英雄登记表没保留这两个标记，v1/v2都把文字当成现行。

- 清单`knowledge/mechanics/stale-upgrade-text-v1.json`：29条，由原始响应推出，测试可重算；由该升级授予的技能（如狙击手·震荡手雷）不算。
- `extractions/v3/`＝v2去掉这些文字的证据（`excluded_facts`保留原文和原因），去掉19组，其中第1轮接受17组。
- **局限**：标记只能识别升级文字。U36重新抓取（2026-11-01）英文零改动、最新补丁7.41f（09-15），基础描述就是官网当前文本，很可能对应7.41f；接口无补丁字段，仍为`patch_verified=false`。

## 8. 复核后事实v4–v7与规则v1（2026-11-03至05）

- **当前入口**：`knowledge/mechanics/current.json`（U113），即`extractions/v20/`、`vocabulary-v13.json`、`rules-v11.json`。v4起不重新抽取，只在冻结的v3上叠加判断，每组用`basis`标明依据。
- **游戏文件**：`knowledge/game-files/`是公开镜像固定提交的快照。“能否被破坏”直接用`IsBreakable`（U48）；字段名不能单独当证据（U51）。
- **词表缺口**：用户发现缺虚无后排查，增加A、B组29项，C组纯属性不进词表（U58、U62、U63）。
- **升级只改数值不记机制**（U65、U66、U72）：放在`numeric_upgrades`；v20起每组带`ruling`写明裁定来源（MK-T6c）。
- **规则层**（U68–U73，已结束；后续U94、U97增至22条）：只说机制关系，不说“该出”。`mechanics_interactions`校验规则并算出来源和目标。
- **局限**：`patch_verified=false`，版本认证放到MK-T6（U66）；`two_ai`不算用户确认；未审候选和可能的漏记留到MK-T5抽查。
- **漏记（MK-T5发现）**：候选靠关键词筛，复核看不到没被筛出的组合；莱恩·妖术、风暴之灵·球状闪电等都没有记录，见`knowledge/mechanics/reviews/recall-check-001/`。
- **派生层**：`profiles/derived-v11/`含英雄档案、装备档案、克制关系图和英雄特性v3，每条带证据链；U5抽查前都是草稿；克制关系是候选，读取规则见`knowledge/mechanics/README.md`。
