# 路线B任务契约草稿：预测“接下来会不会死”（U160，2026-11-17）

**状态：草稿。**方向是用户决定（U160）；下面标“助手建议”的数值和口径等用户确认后冻结。2026-11-17用户要求先做基线（U161），已按本页口径训练，结果见[模型卡](b2-death-risk-baseline.md)；口径确认前不用留出集。

## 1. 为什么改

B0想用规则判断“是不是被抓”，验收没通过（规则判“被抓”的只有约33%–73%用户认同，[B0规则](b0-gank-rules.md)§19、§21）。把它当训练目标，模型会学到规则的偏差。死亡是录像里的事实，没有标签争议，所以改成：

- **预测目标**：某一秒之后的一小段时间内，这个英雄会不会死。
- **类别只作解释**：被抓、自己深入、团战等（`data.death_tags`、`data.gank_depth`）不再是训练目标，只在复盘页上说明“这次死亡是什么情况”。类别有错不影响模型本身。

## 2. 契约内容

| 项目 | 设置 | 依据 |
|---|---|---|
| 评估对象 | 1号位（U132），位置作为参数，不写死（U116） | 用户已定 |
| 样本 | 每场每个1号位，活着时每5秒一个样本 | 助手建议 |
| 标签 | 之后N秒内死亡＝1，否则0；**N＝20秒**（U115暂定的防被抓窗口），同时报告10秒、15秒 | U115暂定；待用户最终确认 |
| 不算的时间 | 已经在挨打（过去3秒受到英雄伤害）之后的样本不用于“预警”评估，单独统计 | 助手建议，待用户定 |
| 哪些死亡算 | 1号位：全部死亡都算正例（高地、大团战中的也算），评估时按`death_tags`分开报告。5号位开发时再定 | 用户已定（U162） |
| 输入 | 只用该玩家当时能知道的信息：己方英雄状态和位置、己方视野里看到的敌人及其最后出现的位置和时间、眼位、兵线、塔、时间、双方装备等级（可见部分）。**不用**敌方不可见时的位置、开雾状态。第2版（2026-11-17）加了自己的保命手段（有几个、几个能用）、己方兵线、己方假眼覆盖、敌方先手英雄（Valve官方定位标签）消失和可见的人数；敌方眼位、雾里的敌方兵线、敌方冷却仍不用 | U6、U55；第2版的特征是助手的选择 |

| 基线 | ①只看时间和血量的规则；②逻辑回归；③梯度提升（sklearn，不加依赖） | 计划B2 |
| 数据 | `data/demos-2026-11`，1678场，非留出1341场；1号位约3000局 | [demo数据卡](demo-data-card.md) |

## 3. 已知局限

- 正例很少（每局死几次，每次只有N秒是正例），要看平均精度而不是准确率。
- “会不会死”不等于“该不该这么做”：有的死是值得的（换掉对面核心）。模型给的是风险，不是对错。
- 死前几秒的样本很容易预测（已经在挨打），所以要把“已经挨打之后”的样本分开，否则指标虚高。
- 高分段数据，不代表其他分段。

## 4. 人工判断还需要多少

- 模型训练和评估不再需要用户逐个判断。
- 仍需要用户的地方：①确认本契约的N和口径（一次）；②模型出来后看少量报警例子，判断“这个提醒有没有用”（每轮约20个，不是逐个定类别）；③复盘页上的类别说明如果要改进，仍要用户意见，但不阻塞模型。
