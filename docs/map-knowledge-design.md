## 1. 为什么做

知识库对地图只有点位（`knowledge/awareness/map-zones-v1.json`：22座塔、2个基地、2个泉水、28个野怪营地中心）。规则里凡是涉及“在哪里”的判断都是近似：

| 概念 | 现在的算法 | 在哪个模块 | 问题 |
|---|---|---|---|
| 在哪一路 | 按地图对角线切三条带（`lane_of`，带宽3000） | `sources.gem_capture_v3` | 野区、河道、三角区被硬算进某一路 |
| 敌方控制区 | 最近的未倒的塔是敌方的 | `data.gank_depth` | 只是塔的远近 |
| 敌方野区 | 离敌方营地中心≤1200 | `data.gank_depth` | 是圆圈，不是野区范围 |
| 高地 | 泉水为圆心的四分之一圆（U140，用户定） | `data.gank_depth` | 不是真实的高地边界 |
| 站位深浅 | 沿泉水连线的距离 | `data.gank_depth` | 不分河道、坡 |

完全没有的：高低地、树林和可走区域、河道、肉山坑、符点等地标、视野范围、路程和时间。后果：归类规则认不出“河道”“敌方野区入口”这类位置；“被抓能不能提前看出来”的探索（`docs/b0-gank-rules.md`§17）里站位只能用一个深浅数字表示。

## 2. 第一版做什么、不做什么

**做（第一版）**：

1. **有名字的区域**：把地图分成几十个多边形区域，每个位置能查到“区域名、归属（天辉／夜魇／中立）、类型（路、野区、河道、高地、基地、肉山区等）”。
2. **地标点**：塔、基地、泉水、营地（从现有文件搬过来），加上肉山坑、符点、前哨等固定点。
3. **读取接口**：一个函数库，输入坐标，输出区域和地标距离。
4. **回放页显示**：事实栏写出区域名，地图上可以叠加区域边界。这是显示，不是规则。

**不做（以后的版本，各自需要单独决定）**：

- 高度和可走格子接入规则（先核对版本和许可，见§4）。
- 寻路、路程换算成时间、TP落点。
- 视野范围模拟（哪片区域被照亮）；眼位知识。
- 改任何冻结的规则或已有产物。

## 3. 产物放在哪、长什么样

地图知识两条线都可能用（路线A以后可能用“打架在哪”），放在**共享底座**：

```
knowledge/map/
  README.md
  current.json              # 当前版本入口：指向下面的文件并记哈希（仿照 mechanics/current.json）
  regions-v1.json           # 区域多边形
  landmarks-v1.json         # 地标点
  third-party/              # 上游导出的高度、可走格子、树（U146），附 SOURCES.md
src/dota_items/data/map_api.py     # 读取接口（共享底座，只用标准库）
scripts/build_map_knowledge.py     # 从草稿生成并校验（共享底座）
tests/test_map_api.py
```

`regions-v1.json`每个区域：

```json
{"id": "dire_jungle_top", "name_zh": "夜魇上路野区", "owner": 3, "kind": "jungle",
 "polygon": [[x, y], ...], "basis": "user"}
```

- 坐标用回放的格子坐标（和解析器v3的位置一致，地图中心16384）。
- `kind`的取值：`lane`、`jungle`、`river`、`high_ground`、`base`、`roshan`、`other`。
- `basis`：`user`（用户画或确认的）、`assistant_draft`（助手草稿，未确认）。和机制知识库一样，不是`user*`的不算用户批准。
- 区域之间不重叠，合起来覆盖可走的全部地图；校验脚本检查这两点。

接口（`data.map_api`）：

```python
region_at(x, y) -> {"id", "name_zh", "owner", "kind"} | None
side_at(x, y, team) -> "own" | "enemy" | "neutral"      # 相对某一方
landmarks(kind=None) -> [...]                             # 塔、营地、符点等
nearest_landmark(x, y, kind=None, team=None) -> (landmark, distance)
```

**2026-11-13查上游的结果**（GitHub公开接口）：

- 我们固定的提交`f793787e`是该仓库最新的一次提交，日期2026-04-03，提交说明就是“7.41”，改动的文件正是`data/elevationdata.json`、`data/gridnavdata.json`、`data/mapdata.json`等，并新增了`logs/741_data.log`。前一次提交是“7.40”。所以上游**声明**这份数据是7.41的；7.41之后的小版本（到7.41f）地图有没有再改，上游没有说。
- 两个仓库（分支和原仓库）都**没有LICENSE文件**，GitHub显示无许可证。`package.json`里写着`"license": "ISC"`，作者devilesk。ISC是和MIT类似的宽松许可证，允许使用、修改、再分发，只要求保留版权和许可声明。但这个字段是原仓库的代码包声明，分支作者新导出的7.41数据没有单独声明；数据内容本身来自Valve的游戏地图。

**问题一：版本。** 上游声明是7.41（见上），但没有用我们自己的录像核对过，当前补丁是7.41f。核对办法（不用联网）：拿已采集的7.41f录像里英雄每秒的位置去撞“不可走格子”，落在不可走格子上的比例应该接近0（飞行、被推的少数除外）；塔的位置和录像实测对比（这部分已做过，误差≤1）。比例明显大于0就说明数据过时，不能用。

**问题二：许可（用户决定，U146，2026-11-13）。** 仓库是公开的；用户决定可以把这份数据放进版本库，注明使用了该库的内容。做法：

- 只放用得到的、整理过的部分（高度网格、不可走格子、树和地标点），不整包照搬；放在`knowledge/map/third-party/`，和我们自己画的区域分开。
- 同目录放`SOURCES.md`：原仓库和分支的地址、固定提交`f793787e`、取得日期、每个文件的哈希、ISC许可声明全文和版权人（按`package.json`：devilesk），并写明地图内容本身属于Valve，本仓库的MIT许可证不覆盖这部分（和`knowledge/hero-capabilities/SOURCES.md`同样的写法）。
- 写明：权利人提出异议就移除，届时`map_api`的高度和可走查询退回“没有数据”，区域查询不受影响。
- 剩下的不确定（助手的判断，不是法律意见）：仓库没有正式的LICENSE文件，ISC只出现在`package.json`；分支作者导出的新数据没有单独声明。这类数据在开源Dota项目里普遍被再分发，风险低，但不是零。

## 8. 局限

- 区域是人画的多边形，边界处会有争议；不同人划法不同，这里以用户的划法为准。
- 区域不等于控制权：塔倒了以后“敌方野区”实际上可能已经是己方地盘。第一版只给静态归属，“当前谁控制”仍要结合塔的存亡（`data.gank_depth.standing_towers`已有）。
- 没有高度和可走数据时，区域查询照常工作，但回答不了“隔着树林”“高坡上下”这类问题。
- 地图随补丁变化；每个版本的地图知识只对应写明的补丁。

## 9. T1、T2的结果（2026-11-13）

### T1：数据和7.41f录像对得上

用留出集以外79场7.41f录像里英雄每秒的位置（176万个）去对“不可走格子”：

| 对法 | 站在不可走格子上的比例 |
|---|---|
| 原样（格子坐标是格子中心） | 0.05% |
| 整体错开128（两格） | 2.0%–2.5% |
| 整体错开512 | 9.3% |

0.05%和飞行、穿树、被推的情况相符；错开两格就高出40倍，说明网格和录像坐标是对齐的。高度数组的方向也核对了：按`[x][y]`读时，高度有变化的格子（悬崖）92%是不可走的，另外两种读法只有68%。

各层的含义（看图得到）：0＝水域，1＝低地，2＝两边基地的平台和野区里的高台，3＝泉水，−128＝地图外。**注意**：不可走格子只标了悬崖和地图边界，树不在里面（树是另外2475个实体），所以“可走”目前不含“被树挡住”。

### 10.2 视野模拟第一版和检验（已做，只是探索）

昼夜按每5分钟交替、开局是白天。三种做法，每种多加一条规则：

|---|---|

**检验**：138场（有眼位缓存、留出集以外），每5秒、每个活着的英雄，问“对方这时看不看得见他”，和回放里记录的实际情况对；正在开雾的英雄不算。共61.5万个样本，其中实际被看见的占44.6%（全猜“看不见”的正确率是55.4%）。

| 做法 | 总正确率 | 实际看得见时模型也说看得见 | 实际看不见时模型也说看不见 |
|---|---|---|---|

| 加高低地（只有高地、高坡算高） | 84.5% | 84.0% | 84.8% |
| 加视线遮挡（河道也算低一层） | 85.3% | 78.4% | 90.9% |
| **加视线遮挡（只有高地、高坡算高）** | **85.7%** | 80.0% | 90.3% |

**怎么读**：

- 只按距离就有84%；加上地形和树只多了1个多百分点，但把“看不见”判对的比例从83%提到90%，代价是“看得见”漏判变多（86%→80%）。
- “看得见却被模型判成看不见”的20%，最可能的原因是视野来源不全：除了兵线最前面那一个点，其他小兵都没有位置；召唤物、前哨、观察者、技能和物品给的视野也没算。

- 结论：这个精度够在回放页上画个大概，**还不够用来当规则或模型的输入**（每5次有1次看得见的判成看不见）。要提高，最值得补的是小兵的位置（要改解析器，重抽每秒状态）。

没有做的：把视野覆盖画到回放页上（现在页面只画了眼的1600圆）；任何规则或特征都没有用模拟结果。

| 远了300–1000 | 16% |
| 远了1000以上 | 13% |

实际看不见、模型说看得见的：90%的英雄并没有隐身，就是在距离内、模型没挡住而游戏里挡住了。

**试过调参数，没有用**：距离统一加100、200、300，英雄夜间视野800改1000，去掉树的遮挡——在一组比赛上调、在另一组比赛上确认，最好的仍是现在的设置（另一组上88.2%，和不调一样）。加距离会把“看得见”判对更多，但“看不见”判错更多，两边抵消。

**结论**：这种“画圆加64单位格子的遮挡”的近似，上限大约就是88%。错不在缺来源，也不在某个数值，而在遮挡的精细程度：游戏里的战争迷雾比64单位的格子细，树会被砍，视野边缘和时间上都有我们量不到的细节。要明显超过88%得按游戏的方式重做迷雾模拟（更细的格子、每棵树的存亡），工作量大而且不保证成。**建议**：视野模拟停在这里，只作“大概”的参考，不进规则、不当模型输入；回放页要不要画由用户定，画的话写明约八分之一会错。

### 10.5 崖边检验：64单位格子在崖边拖累多少（U186，2026-11-20）

用户问64单位的地形精度够不够。`scripts/vision_cliff_check.py`，`reports/vision-cliff-check-2026-11-20/`：同样138场、61.5万个样本、最好的那一版（视线遮挡、只有高地高坡算高、全部小兵），按英雄离最近崖边（高度层1和2的交界）的距离分组：

| 离崖边 | 样本 | 正确率 | 看得见却判看不见 | 看不见却判看得见 |
|---|---|---|---|---|
| <64 | 6486 | 86.8% | 24.6% | 7.8% |
| 64–128 | 8240 | 87.7% | 23.9% | 6.9% |
| 128–256 | 22968 | 87.8% | 22.7% | 7.6% |
| 256–512 | 62272 | 89.2% | 20.4% | 6.8% |
| ≥512 | 515204 | 87.7% | 13.8% | 11.1% |

“看得见却判看不见”的4万个样本，按离目标最近、在距离内的来源被什么挡住分：没有来源在距离内62%，被树挡24%，目标比来源高13%，中间有更高的地面0.3%。被挡的来源大多离崖边500以上。

- **崖边的总正确率不比别处差**（86.8%–89.2%对87.7%），崖边附近只占约16%的样本。崖边的错偏向“挡得太严”（漏判看得见多、误判看得见少），说明高度判断在崖边偏保守，但对总数影响很小：即使崖边的漏判降到远处的水平，总正确率也只多约0.5个百分点。
- **树比崖边重要**：被树挡掉的占漏判的24%，全部修好上限约1.6个百分点。现在每棵树按占满一个64单位格子算，比真实的树干大，而且被砍的树不知道。
- **没有来源在距离内**的占62%，但§10.4试过加距离、加来源都没有净提升，这部分多半是视野边缘和时间上量不到的细节。
- **结论（助手）**：崖边细化高度不值得做。如果还要提高，下一步是树：①树按真实半径（而不是整格）做遮挡，不用改解析器，可以先试；②被砍的树要改解析器。两步加起来上限也只有一两个百分点，视野模拟仍只作参考。

### 10.6 树按真实半径遮挡；被砍的树查不到（U186，2026-11-20）

**历史采样实验**（2026-11-20审查）：以下结果来自沿线采样且跳过端点格的旧实现。精确圆盘与线段相交的结果单独评估。

**树的半径**：`scripts/vision_tree_check.py`，`reports/vision-tree-check-2026-11-20/`。原来每棵树按占满一个64单位格子算；这里改成视线经过树中心多少单位以内才算挡住。比赛按编号交替分成两半，一半上挑、另一半确认：

| 整格（现在） | 87.74% | 87.89% | 85.7% | 89.7% |
| 半径32 | 87.75% | 87.87% | 86.4% | 89.1% |
| **半径48** | **87.96%** | **88.05%** | 84.5% | 90.9% |

**被砍的树**：用户同意改解析器（2026-11-20）。查了一场7.41f录像（9080976703，用兼容版解析库），**没有直接的砍树记录**：

- 实体：没有树或树状态管理的实体类；游戏规则实体的224个字段里没有和树有关的。
