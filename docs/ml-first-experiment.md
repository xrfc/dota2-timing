## 1. 先区分两个问题

| 问题 | 可以从数据学习什么 | 不能声称什么 |
|---|---|---|
| 相似阵容的玩家买什么 | 行为模仿、装备出现频率与条件分布 | 玩家购买就是最优决策 |
| 当前下一件值得完成什么 | 需要时间截点、已持有装备、合成/送达和未来标签 | 购买日志的一条记录就是完成/可使用时间 |

产品目标仍是后者。第一项可以成为学习基线，但必须显式命名为行为预测，不能悄悄
替换产品目标。最终六格只能表示终局库存，不能充当整场购买集合或下一件装备标签。

## 2. 主宰数据可行性审计（初版已实现）

2026-10-13初版：已实现[审计CLI及真实三场探查](data-feasibility.md)，保留全体尝试分母、
未知/截尾、去重冲突和来源哈希；未实现角色/补丁认证、完整物品映射或训练标签生成。
后续已完成固定扩展与[7场语义核验](data-semantics.md)：购买汇总是同源派生，位置为赛后估算，
成装/送达标签仍未验证。
下列清单仍是完整审计目标，不能因初版工具可运行全部标为完成。

复用现有 `sources/opendota.py`、规范化和证据哈希能力，不另起采集框架。
先做小批公开比赛的只读采样与本地审计，再根据可用率确定是否批量采集。
首版范围沿用7.41f、一号位主宰、无命石；不能仅凭hero_id、优势路或胜方身份推断位置。

每场审计保留以下字段及拒绝原因：

- `match_id`、来源、获取时间、原始响应SHA-256、解析/规范化版本。
- 补丁证据、十名英雄/阵营/slot、主宰身份、一号位与高分/职业来源证据。
- 购买日志是否缺失、时间范围、同秒多件、物品键映射、配方/消耗品处理。
- 库存/合成记录是否存在、是否覆盖需要的截点；字段存在不代表语义核验通过。
- 已知重复、冲突、缺测、短局截尾，以及每个拟用标签的可用/不可用理由。

先输出全体采样分母与各项可用率，包括失败和排除的比赛；不得只保存成功样本。
审核原始字段到样本标签的实例后，才冻结预测时点、窗口和候选词表。
未证明连续覆盖时，“没看到购买”是未知，不是负标签。

## 3. 候选实验与选择条件

优先评估“十英雄阵容 → 固定窗口内观察到的目标装备购买行为”的可行性：
输入只包含开局已知阵容、目标英雄/角色和适用补丁，不使用最终胜负、终局经济、
游戏时长或未来装备。窗口与装备集合待上述审计确定，不能为提高指标事后挑选。

若目标成装在购买日志中不可靠，就拒绝这一标签设计；先补合成/库存证据，
或明确另建终局库存实验，不能通过猜配方把它宣称为“下一件完成”。
旧 `coach-features/1` 包含位置和经济，也没有十英雄阵容编码，不能直接冒充此实验输入。
新实验需要独立版本的样本契约、特征构建、任务掩码和准入实现；本轮均未修改。

## 4. 从基线到深度学习

1. **频率基线**：只在训练比赛统计候选装备频率；验证集选超参数。
2. **线性基线**：区分友/敌阵营的multi-hot英雄编码，按最终标签定义使用
   多标签逻辑回归或单标签分类，不混用两种目标。
3. **Embedding + MLP**：仅在基线、数据量及独立评估可复现后加入；对比参数量和过拟合。
4. **时序决策模型**：待库存/经济等输入及成装标签获准，再推进“下一件完成”的目标。

按比赛划分，整场与其所有时间窗只能归属一个集合。去重在划分前完成；
频率、词表学习、标准化和缺失填补只使用train；测试集不参与调参。
重复玩家引起的相关性另行统计，不能把比赛独立说成玩家完全独立。

冻结评估时记录数据/代码哈希、采样与排除方案、随机种子、分割清单及指标：
多标签报告micro/macro PR与Recall@K，单标签报告Top-1/Top-K；两者都报告各类支持数、
未知/截尾比例及频率基线差值。另做去掉敌方阵容的消融，验证是否真正利用阵容信息。
质量差值不是胜率提升，也不是“最佳决策正确率”。
