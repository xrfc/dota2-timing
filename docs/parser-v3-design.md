# 解析器v3设计：从demo补全每秒状态（2026-11-09）

状态：**设计稿，待用户确认范围后实现。** 起因：用户要求先做“B：补提取技能冷却”，并把解析器设计完整（2026-11-09）。

## 1. 目标与原则

- **补齐路线B需要、现在没有的状态**，首先是技能和物品冷却；顺带把demo里容易拿、以后两条线都用得上的状态一次性设计好，避免以后反复重解析。
- **不影响正在跑的采集。** 后台采集每场都调用现有解析流程（`dota_items.workflow.cli prepare`）。v3做成**第二遍抽取**：独立模块和脚本，读已保留的demo，输出新文件；现有`parsed/<id>.normalized.json.gz`不动。
- **字段名和取值都来自实测**，不凭印象。下表“已验证”的字段都在2026-11-09的探针里读到过（`data/demo-pilot-2026-11-08/9077127446`，第900和1200–1240游戏秒）。
- **缺失记null，不记0。** 读不到和值为0是两回事。

## 4. 采样与对齐

- 每**游戏秒**一次，和现有英雄位置同一时刻对齐（`game_time`取整秒），暂停期间不重复采。
- 冷却这类“剩余秒数”字段，在两次采样之间也能推算；施放时刻以战斗日志为准。

## 5. 输出格式

- 每场一个`state-v3/<id>.jsonl.gz`：每行一个游戏秒，含`heroes[10]`（P0、P1）、`world`（P1）、`units`（P2）。
- 文件头一行写：解析器版本（`gem-state-capture/3`）、Gem版本、demo的SHA-256、字段表版本。
- 预计体积：P0＋P1每场约2–4MB压缩后（未实测）；P2按“兵线前沿”方案再加约1MB。实现后先用10场实测。

## 6. 验证（实现时逐项做，结果写报告）

1. **冷却和战斗日志对齐**：战斗日志每次`ABILITY`/`ITEM`施放后，下一秒该技能/物品的剩余冷却应接近冷却总长；转好前不应再出现同一技能的施放。
2. **TP**：每次传送施放后格子15的冷却跳到TP冷却总长。
3. **单位状态位解码**：拿战斗日志里眩晕、沉默、妖术等`MODIFIER_ADD/REMOVE`的时间段，对照`m_nUnitState64`哪一位同时变化，确认每一位的含义后才输出解码后的布尔值；未确认的位只保留原始掩码。
4. **抽查**：几场比赛在现有录像查看器里人工对照。

## 7. 可知性（路线B使用时）

这些都是**全知数据**（录像里什么都看得到）。路线B把它们当输入时，必须按阵营可见性过滤：敌方的冷却、血蓝、物品默认**不可知**，只有在当时可见、或看到施放时才算已知（U6，`docs/replay-quality-2026-10-26.md`的阵营层）。这一层在B0/B1的任务契约里定，解析器只负责如实记录全知状态和可见性。

## 8. 运行方式

- 新模块`sources/gem_capture_v3.py`（不改v2），新脚本`scripts/extract_state_v3.py`：对`data/demos-2026-11/demos/`里的demo逐场抽取，可续跑、每场回执、不覆盖、读回校验，和采集脚本同样的风格。
- 机器内存5GB：和后台采集错开运行（或一次一场），避免同时解析两场。
- 已采的demo都能重抽；采集完成前可以先抽已有的。
