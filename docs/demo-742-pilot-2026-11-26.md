## 3. 需要改进的地方及次序

### 第一优先级：精确选择版本，统一质量验收

1. **采集入口支持精确补丁。** 现有 `latest_patch_start()` 自动跟随最新补丁，`check_metadata()` 只有起始下界；应增加显式版本与结束边界，并在 SQL 发现阶段应用完整时间条件，避免花元数据请求验证必然排除的候选；分别记录官方时间推断、OpenDota patch、实测 build。`--once` 是一个候选批次，不能作为少量试采的次数上限，应另设候选/尝试/字节/耗时预算。
2. **完成性必须分层。** `require_complete_parse()` 只检查解析异常；合成的 16 字节录像头可无异常返回空结果。基础标准化会拒绝 ID=0，因此不是“空录像已进入基础数据集”；但 v3 等旁路会用命令行 ID 填头，需统一检查真实 ID、结束标记、十名英雄、时序及通道覆盖。结束标记本身也不能保证最后一个字节完整。
3. **保存可核对的来源身份。** 现有回执缺少显式 patch/build/compat 实现身份，默认压缩后清掉 workspace 会同时丢掉 import manifest 与 raw。应至少长期保留来源/生产者摘要和质量摘要；解析器实际导入路径与源码身份要纳入预检，不能只写 `gem-dota=0.10.0`。
4. **缓存通过复核才可复用。** 原采集器会凭已有 demo 或回执跳过部分步骤，重试可能清理既有 workspace。应按输入/生产者摘要验证复用条件，坏缓存、未完成输出、解码失败分别保留，写入采用原子发布；禁止将未知缓存直接算作成功。

### 第二优先级：按阶段恢复，降低重复工作

5. **发现、下载、解析、质量验收分开保存状态。** 404、网络失败、预算暂停、解码失败、质量待复核不是同一种重试条件。每次解析前检查磁盘，对失败 workspace 有可审计的保留/清理规则；网络恢复继续下载，解析器修复重放本地归档。Range/ETag 续传只能在服务器支持且身份一致时启用。
6. **减少多次完整解析。** 当前基础、v3、小兵/额外实体分别过一遍，且多处把整场 JSON/行列表载入内存。建议由 `sources` 提供一次解析、多观察器、流式写出；编排决定启用哪些通道，CLI 只负责参数和输出。保留冻结生产者，使用显式迁移及新旧输出对照，不能直接覆盖历史产物。
7. **区分空值与未知。** 某些可见掩码使用 `or 0`，部分物品槽未出现；缺字段、已记录为空、机制不适用不能混为一谈。冷却键非空只是覆盖检查，还需对照施放事件；营地/道路/可见性需用版本对应的地图另验。不能用错误的默认值填满特征来通过质量门槛。

### 第三优先级：建立持续支持的回归样本

8. 先复用 [PR #30](https://github.com/xrfc/dota2-timing/pull/30) 中尚未进 main 的输入覆盖审计（实现 `cfa6107dd3b59ee1eca2d48444b6d3cb33cd9963`），补精确字母补丁、build、来源摘要及非空检查。避免再做一套互不一致的“完整”判据。
9. 固定旧/新补丁的小型回归集，覆盖完整、截断、压缩格式、新英雄及关键字段；先对照兼容层与新 Gem，再决定生产升级。7.42 Workshop 包先验塔/门/营地坐标，再验高度、通行和视野。之后才登记模型支持状态；模型效能评估另用授权协议，不能拿这批工程样本推导模型准确率。

已有预算互斥、失败请求计数、原 demo 保留、大小上限、gzip 读回一致性和串行解析都值得保留。这里提出的是在这些保障上补版本与质量闭环。

后续生产实现按既有架构拆分职责：`contracts` 用标准库定义版本/通道/质量结果；`sources` 负责网络、解压、Gem 事件及真实 parser 观察；`data` 校验标准化数据及通道质量；`workflow` 管理阶段、预算和恢复；脚本仅提供 CLI。数据层不依赖 workflow，sources 不依赖 data。临时试采通过脚本函数编排是本轮执行措施，不应直接变成库模块对脚本的长期依赖。新增生产模块再登记架构归属，冻结旧生产者按显式迁移处理。
