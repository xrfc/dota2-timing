页面允许直接看分析，也保留先独立判断的入口。直接看分析仅记录已看过；此后提交的意见标记为看过分析后的意见。可选抽看的三个场景仅使用当时装备、队友距离取样。全部片段保留以便查阅，无逐条评分要求。


路线 B 的行动比较、因素表和逐段复核格式见[决策总架构](decision-framework.md)。

在真实录像中停在一号位刚补完一刀的时刻。先看过去十秒己方能看到的敌人、最近露头时间、队友位置及当前自身状态，在页面选继续、撤退或证据不足。首次判断和笔记存在当前浏览器。提交后才加载随后六秒的动作和事前规则草案，再点击才加载二十秒内的死亡与线上补刀。三个时点的敌方坐标均按当秒己方视野过滤。

## 一次运行，交付待判断片段

在保存本地报告的项目根目录运行以下命令。它会查找 `reports/action-comparison-{lane,jungle,wave}-001` 下的报告，自动核验材料、读取本地评审库并启动回环门户。也可以用 `--review-dir <报告目录> ...` 指定仅有的一种或两种模式。每种模式只选一份活动报告。

```bash
PYTHONPATH=src .venv/bin/python scripts/decision_review_handoff.py --serve
```

本机 2026-11-22 重建的报告位于 `reports/local-review-20261122/`。从项目根目录运行以下命令，使用新报告并接续原私有评审库。

```bash
PYTHONPATH=src .venv/bin/python scripts/decision_review_handoff.py --review-dir reports/local-review-20261122/action-comparison-*-001 --serve
```

启动时，终端给出登录网址；当库中没有有效邀请码时会签发新码。先登录，再点终端列出的片段链接。评审人提交独立选择后，组织者在终端按回车刷新。不同评审人各用自己的邀请码；如需为另一人签发，组织者在终端输入 `i`。仅预览且从未提交的记录保存在原浏览器。已有门户运行时可去掉 `--serve`，按需指定 `--db` 和 `--portal-url`。默认本地门户端口为 8798。只需检查材料或在自动化中读取结果时，加 `--json`。读取现有报告时不会写入，可以通过 `--reviews <导出.json>` 使用已有导出。

若手头只有原三场 7.41f 采集目录，用下列命令先生成报告再开评审。已有的标准化录像、状态采样和 extras 会复用；只有原始压缩录像时，准备器会生成缺少的派生文件。录像按 `demos/<比赛编号>.dem.bz2` 或 `.dem.zst` 放在采集目录内。若缺本地 meta，仅原三场允许使用已核验的公开记录。OpenDota 的补丁号均为 60，三场 9080976703、9081112027、9081112126 的开局 Unix 秒依次为 1794102760、1794114835、1794114815，均在 Valve 的 7.41f 发布至 7.42 发布之间。准备器再用实际解析出的比赛编号核对录像身份；已有元数据冲突时会报错。报告生成器只创建缺少的目录。需要保留旧报告和原判断时，选择新的 `--root`。若本地缺少 7.41 地图，可显式加 `--fetch-741-map` 获取固定提交的三份文件并验证 SHA-256；来源是 leamare/dota-map-coordinates 和 gem-dota，地图内容属于 Valve。

```bash
PYTHONPATH=src .venv/bin/python scripts/decision_review_handoff.py \
  --demo-root data/demos-2026-11 --root reports/review-round --serve
```

- **先核对材料。** 工具检查片段与比赛身份、留出标记、可见证据的时间先后、6 秒动作和 20 秒结果，重算到场与受击对照。新报告按比赛终局和最后采样秒中较早者截断。旧报告没有这两个字段时，结果会显示无法独立核对终局的段数。缺文件或出现矛盾的片段进入材料清单。使用本地总入口启动门户时，只开放通过核验的片段。
- **再抽查或裁定。** 三种报告合计每轮默认最多显示 5 项，优先处理独立意见的分歧，再列尚未覆盖的代表片段。独立意见一致为“证据不足”时，记录为已抽查、暂不排序。已有明确分歧或具体行动与“证据不足”并存时，组织者可输入对应编号、选择行动并可附一句理由，也可以保留“证据不足”。处理完一轮可刷新查看下一轮。
- **按版本接续。** 新版邀请门户把已提交意见绑定到当时展示的片段证据。旧客户端的无版本记录和其他版本的记录都保留并分别统计。裁定保存在私有的 `friend-review-private/adjudications.sqlite3`，重新运行会恢复；证据或独立首次意见变更后重新核对。个人在另一个浏览器看过但从未提交的活动无法从数据库还原。
- **读结果。** `human_judgment` 表示已具备本轮人工判断所需材料，`complete` 表示本轮抽查与已发现的争议已处理。`data_required` 和 `repair_required` 会列出材料位置及原因，命令返回 1。需要查看逐项机器核验结果时，可用 `scripts/audit_decision_reports.py --review-dir <报告目录>`；其中包含事后证据，供组织者查看。

## 精简人工抽查

在带线、补刀前和打野报告中点击“打开下一段抽查”。每份报告固定选最多 5 组，每组只需一条独立判断。“证据不足”也是有效判断。全部片段仍可从下拉框打开。

分组使用决策秒的四类证据：队友距离、可见近敌或多名敌人失踪、队友受击支援线索、检测到的就绪保命手段。先取片段最多的一组，再优先覆盖尚未出现的证据取值；分数相同优先片段多的组，再按报告顺序。选组不会读取后续动作、结果或评审答案。五组是本次实现的工作量默认值，同组仍可能有不同的正确选择。

点击“直接看分析”后，该片段退出个人盲评候选，系统会找同组的其他片段。离线页面按本机保存的首次意见计数；邀请页面以当前评审人已提交的独立首次意见计数，未提交的判断会优先重新打开。可复用的旧报告只需同步最新版页面资源。进度显示已覆盖的情景组数，用于发现解释缺口；估计整体准确率仍需要单独设计的抽样。

## 取样与判断

从第 15 分钟开始，用前 15 分钟补刀推断的一号位亲自补掉敌方近战、远程或旗手兵作为起点。要求距己方兵线前沿不超过 1000，当前及前四秒没有受到英雄伤害，同一英雄两个起点至少隔 120 秒。该口径能找到吃完一刀后的选择，会漏掉提前放弃整波线的决定。

草案使用探索性阈值。最近队友至少相距 1500 或无队友在场，同时可见敌人在 1600 内或至少两名敌人消失满十秒（含从未露头），提示考虑撤退。五名敌人全部可见且都在 1600 外、1000 内有队友，倾向继续收线。控制状态缺失、无法移动或证据不足时保留判断。技能就绪估计只作为人工解释线索，尚未推断敌人抵达时间或队友实际救援能力。

六秒内再次补刀是继续收线的可观察依据。向己方一侧移动至少 350 且远离原兵线前沿至少 250 是后撤依据。两者同时发生、位置跳变、缺帧或两者都不满足时保留为动作不明。

## 首批结果与下一步

已有三场 7.41f 非留出录像产生 47 段，20 秒结果窗均完整，均存活。录像动作可辨为继续收线 25 段、后撤 2 段，其余 20 段不明。草案提示撤退 23 段，其余 24 段保留判断。13 段提示撤退后玩家继续补兵。下一步优先人工盲评这些分歧片段，记录支持短留的收益、保命手段与撤退路线，再检查草案是否过于保守。当前数据不足以估计判断准确率及另一种选择的结果，也没有覆盖 7.42 实战。

## 下一阶段：带线、转野与支援

现有 47 段带线案例保留供人工逐步评审。转野和支援另做案例，允许多种理由同时成立。候选时刻也应覆盖未补到兵便离线，以及清完一组野后决定下一步的玩家。

- 离线原因分别记录风险与机会。敌人消失是风险线索；队友遇战、有机会反打、自己能否及时到场，是另一组证据。仅凭离线轨迹无法确定动机。
- 比较继续打野、换区和支援时，同时呈现己方能看到的威胁、附近存活队友的位置与可能到场时间，以及放弃当前资源的代价。
- 区分“玩家知道自己曾在线上露头”“录像显示对手看到了玩家”“对手可能猜到下一处野区”。敌方真实视野留到事后核验。动向可预测性可以用最后公开位置、离开方向和可达野区解释；路线有多个合理分支时保留不确定性。
- 首轮验证用相似局面对照：同样有人消失，有队友能接应与孤身深入是否应给出不同判断；同样能收一组野，有可及时支援的战斗时是否应改变选择。

地图随所选时刻展示己方仍在场的侦察守卫、岗哨守卫，以及每个敌人最后连续可见的最多 12 个逐秒位置。视野中断即截断轨迹，最后露头点标注距当前的秒数。眼位依据录像插眼和移除记录估算在场时间；地图可切换己方普通地面视野的估算边界。每个 128 单位格取中心点，结合昼夜半径、高低差及静态树木估算。岗哨守卫符号单独展示。

在首批 47 段有敌方坐标的 496 条英雄时刻记录上，格内/格外与录像可见标志相符 447 条。实际可见 98 条中识别 80 条，实际隐藏 398 条中正确判为格外 367 条。该对照只检验英雄经过的位置，不能测出整张地图边缘的距离误差；隐身、临时技能视野、砍树等都会造成差异。

装备随选择的帧更新。己方显示当秒随身装备，敌方显示最近一次己方有视野时的装备快照和时间；无快照显示未知。背包装备另标，控制装提示只取主装备栏中的紫怨、血棘、碎颅锤、深渊之刃和邪恶镰刀。提示仅用于讨论先手与脱身条件，未评估敌方装备冷却、触发概率及击杀伤害。

## 到场、敌方接触、发育与兵线取舍

同一生成器现支持 lane、jungle、wave 三种模式。沿用上面的三场录像，使用 --mode wave 生成补刀前的兵线取舍案例。英雄距离己方兵线前沿不超过 1000，800 内有至少一个按普通地面视野推算可见、距该前沿不超过 1000 的敌方线上小兵，且当前及过去六秒无本人线上补刀。同英雄间隔至少 120 秒。随后六秒是否补刀或拉开留到动作文件，取样无需知道英雄未来是否死亡。

行动比较使用同一决策秒。支援估算比较立即出发与多刷六秒，列出固定目的地下直线和多绕三成两种距离情景；有明确位移资料或可用卷轴与己方塔时另列条件。敌方接触按最近露头及简化移动情景，列明可见装备与己方应对。发育以此前二十秒补刀、己方兵线和附近营地描述可能去向。营地存量、下件装备目标、每刀金币与击杀概率仍缺少依据。队友后续受击、实际补刀只在结果中揭示，最近受击秒不能独立确定交战结束。

## 邀请朋友在线评审

在本机以 scripts/friend_review_server.py 启动独立门户。三个 action-comparison 报告目录名使用生成版本 -001；部署时将 scripts/lane_decision_assets 中的 HTML、JS 和 CSS 同步至三个站点。服务只监听回环地址，通过能保留 Host 的 HTTPS 反向代理转发门户端口。每位朋友单独分发一个邀请码；重复使用同一码会进入同一评审身份。点击提交后保存到服务端，受邀者只能读取自己的记录。数据库与邀请码只放在忽略版本控制的私有目录。

```bash
.venv/bin/python scripts/friend_review_server.py --db reports/friend-review-private/reviews.sqlite3 --port 8798 serve
.venv/bin/python scripts/friend_review_server.py --db reports/friend-review-private/reviews.sqlite3 issue
.venv/bin/python scripts/friend_review_server.py --db reports/friend-review-private/reviews.sqlite3 export
```

历史步行统计的赛后截断尚待原三场录像重算。现在核验按终局与状态末秒共同截断。步行耗时核验可运行 PYTHONPATH=src .venv/bin/python scripts/check_support_travel.py。固定八秒终点的 119 段中，39 段落入直线与多绕三成之间。按每段实际终点回看，只校验移动尺度。结果阶段另列玩家是否靠近决策秒的队友位置。

119 段连续移动中，以起点移速换算，每秒坐标连线比首尾直线多出的耗时中位数为 1.46 秒。实际八秒减去连线估时的有符号差值中位数为 +0.07 秒；正负偏差可抵消。直线与绕行三成的平均绝对误差分别为 2.55 和 2.94 秒。 逐秒连线会漏掉秒内转向；残差还包含移速变化。终点取自事后录像，只用于核验。

兵线判断使用本秒公开的阵亡状态。仍在复活倒计时的敌人从失踪与接近威胁计数中排除；只有坐标缺失时，继续按视野记录估算。

7.41f 的回城卷轴消耗 75 魔法。支援估算只在当前魔法足够时给出立即传送时间；魔法缺失时页面提示待确认。

在线页面按评审者和片段在当前浏览器保存首次选择与提前看过分析的标记，刷新后可继续编辑当前意见。点击“提交本段评审”才会写入服务端。

## 事后核对支援步行耗时

揭示结果时，页面将直线和绕行三成两种步行估时，分别与同一个支援对象在随后 20 秒内实际受到敌方英雄伤害的秒点对照。等六秒的情景沿用决策时的位置、移速和目的地，将两种到场估时各加六秒。估时等于受击秒计为同秒到达。结果只描述到队友原位置的条件，队友可能移动，能够到场也不能证明可以施救。

已有同格式报告可以直接导出逐段 CSV，无需重新解析 demo。在项目根目录运行以下命令，参数替换为本地已有报告目录。

```bash
PYTHONPATH=src .venv/bin/python scripts/check_support_travel.py \
  --review-dir reports/lane-decisions-local reports/jungle-review-local > support-windows.csv
```

每行保留比赛、英雄、决策秒、支援对象、两个出发方案的步行耗时、实际受击秒点以及观察窗是否完整。`both_before_hit` 表示两个步行情景都能在某次受击之前或同秒到达；`direct_only` 表示仅直线情景满足；`after_observed_hits` 表示两种估时都晚于完整观察窗内的最后一次受击。没有后续受击或缺少路线时记为 `unknown`。录像提前结束时，已经看到的受击仍可用作正向证据，推断会错过后续受击则保留未知。没有支援对象或旧报告缺字段的片段仍占一行，原因写入 `reason`。表中无草案评分或训练标签。
