## 1. 为什么采用当前组合

| 决策 | 当前理由 | 代价与边界 | 何时重新选择 |
|---|---|---|---|
| Python 3.11+ | Gem、数据工具和未来 PyTorch 共用生态；减少语言间传递成本 | 不能靠普通线程解决 CPU 解析瓶颈；JSON 对象占内存 | 实测发现热点后考虑多进程、列式读取或局部原生实现 |
| argparse CLI + venv | 标准库足够表达当前命令；没有常驻服务就能完整操作 | 缺少交互式进度、任务取消、可视化筛选；依赖未完全锁定 | 日常记录显示 CLI 成为主要使用障碍时增加界面 |
| Gem 可选解析器 | 不从零维护 Dota 协议；项目聚焦游戏语义与训练数据 | 解析器和补丁变化可能改变字段，安装成功不证明语义正确 | 固定真实样本暴露 Gem 无法提供必要字段后再比较解析器 |
| Pydantic 2 | 一处定义配置、模型、预测约束并生成 Schema | 对游戏事实无验证能力；当前未统一 strict 类型模式 | 输入不兼容实际发生时收紧类型，按版本迁移 |
| JSON / JSONL | 人能直接检查；数据包、清单和证据容易携带与比较 | 大文件需全量载入，嵌套对象和多份复制成本高 | 时序扫描成为训练/内存瓶颈时引入 Parquet/Arrow |
| SHA-256 + 复制快照 | 让训练绑定明确数据版本；标注变化不影响旧快照 | 重复存储、全量哈希扫描；不提供物理只读或签名 | 空间/校验成本显著后采用内容对象复用并保留验证边界 |
| SQLite 解析缓存 | 单机索引、事务和查询无需数据库服务 | 外部 JSON 不受 SQL 事务保护；旧路径为绝对路径 | 新 catalog 全量改写或多任务查询成本明显时统一元数据层 |
| 子进程适配器 | 训练框架和管线解耦；便于保存退出码、日志、产物 | 共用 Python 环境；非沙箱；只控制直接子进程超时 | 出现依赖冲突、分布式训练或无人值守任务时增加执行后端 |
| 静态 HTML | 无前端构建依赖、离线打开、便于交付事实和预测 | 无地图轨迹、在线任务进度和复杂交互 | 确定复盘交互需求后增加本地 UI 或 Web UI |
| HTTPX + OpenDota 备用入口 | 保留已有的比赛 JSON 获取能力 | API 返回可能缺购买/时序；缓存语义弱于新工作区 | 双来源确有需求时统一来源和修订协议 |

### Python 和模型框架

Python 是已采用的实现语言；**PyTorch 尚未安装为项目依赖，也没有训练实现**。下一阶段优先考虑 PyTorch，因为自定义时序网络、损失和训练循环较直接，CPU 调试后可切到 GPU。它应先作为模型适配器的依赖，保持基础数据工作流能独立运行。

TensorFlow/JAX 同样可通过适配器接入。除非已有团队经验或明确的编译/部署需求，暂时没有为它们增加一套实现的收益。模型和数据契约应保持独立于具体框架。

### Gem 和数据语义

当前约束 `gem-dota>=0.10,<0.11` 限定了兼容范围，但没有精确锁版。Gem 给出原始结构，项目仍需负责购买含义、暂停时钟、位置/经济单位和缺失规则。继续使用 Gem 的前提是固定回放集上的语义核验；需要另一解析器时先作为独立来源对照，不能直接把两套事件相加。

### JSON 和 SQLite 并存

两者目前承担不同任务：SQLite 索引旧解析缓存，JSON 管理新工作区及快照。对少量单机数据，这能先把协议做清楚。缺点是 catalog 全量读写、查询能力有限，且出现两套持久化边界。

未来可让 SQLite 管理比赛、来源修订、标注、任务状态；大文件仍留在文件系统/对象存储，JSON manifest 继续作为可交换快照。迁移必须提供备份、旧新身份映射和恢复验证，不能仅把文件搬进数据库就宣称一致性问题解决。

### 子进程和服务

子进程让主 CLI 不需要了解网络结构或权重格式，但当前训练器仍使用同一解释器，并拥有工作区访问权限。接口适用于自己维护的程序；它不是远程执行任意脚本的服务设计。

现在不需要为了“云端可运行”先引入 Docker、Redis、Celery 或 Kubernetes。普通云端 Python 环境能运行现有 CLI。若需要长期后台任务，先补齐幂等、心跳、取消和进程树生命周期，再用本地 worker 或服务队列承接。

## 2. 当前最值得优化的顺序

### P0：先补真实数据与追踪

1. 固定有权使用的少量真实回放，覆盖暂停、赛前购买、重复购买、死亡和采样缺失；对购买、位置、经济做双向人工核验。
2. 保存 parser/adapter 精确版本、原回放与来源哈希、代码版本、采样规则和标签来源到快照；记录标签修订。
3. 建立完整性、覆盖率、预期过滤/异常丢弃计数，区分“导入成功”和“可用于该训练任务”。
4. 持久化纳入/排除原因。现在 excluded 只在命令输出中，需要手动留档。
5. 收紧自定义 JSON 的时序边界，补 raw 时间映射验证与缺少独立证据时的状态。

验收：能够解释每场为什么入组、哪些字段未验证、每条训练观察来自哪里；系统性时间错误和不完整输入可被检出。关联 D01/D03/D05/D09/D10、V01–V04。

### P1：让长任务可靠运行

1. 把 Gem 解析放到可管理的独立进程，设置超时和资源预算；保持单场失败后批次继续。
2. 记录每阶段耗时、输入/输出体积、峰值内存、缓存命中及失败原因。
3. 为运行增加心跳和陈旧状态识别，正确终止进程树；区分可重试错误和输入错误。
4. 对数据包发布、catalog 提交、模型登记做故障注入，验证旧产物仍可用。
5. 提供可复验的备份/恢复和迁移流程；逐步把 doctor 扩展到模型、运行与报告。

验收：超时、取消、异常退出和重启不会把任务误报成功；恢复步骤可执行。关联 D04/D06/D07/D11。

### P2：依据实测优化吞吐与存储

当前没有性能基准，不能承诺倍数提升。先固定样本、机器、解析版本，分开测冷缓存/热缓存，并记录逐场耗时；样本足够时再报告中位数和 P95。

| 实测瓶颈 | 候选改进 | 验证方式与取舍 |
|---|---|---|
| Gem 解析占大部分耗时 | 有界多进程、按回放内容复用解析结果 | 对比每小时比赛数和峰值内存；并发数按内存预算限制 |
| 全量 JSON 读取/对象构造占内存 | 按玩家/通道分片，Parquet 列式时序，Arrow 读取 | 比较相同训练窗口吞吐/RSS，保持时间和 null 语义一致 |
| 数据集复制占磁盘 | 内容对象池、reflink 或受控引用 | 搬迁/删除/备份验证必须通过；硬链接可被共同修改，不能直接替代独立快照 |
| catalog 读写随数据量增长 | SQLite 元数据索引与迁移 | 对比导入/筛选耗时，验证事务与文件发布顺序 |
| 重复扫描哈希耗时 | 内容对象缓存与分层校验 | 仍在重要交接点验证；不能仅用 mtime 取代证据校验 |
| GPU 等待数据 | 预先生成窗口、批量读取、DataLoader 预取 | 保持同一 split 和特征结果，测样本/秒与 GPU 利用率 |

Parquet 更适合大量规则时序列，原始证据和小型清单仍可保留 JSON。DuckDB 适合后续跨快照分析，但不是当前必需依赖。对只有几场回放的阶段，正确性与执行恢复通常比压缩率更值得投入。

### P3：明确需求后改善使用体验

先记录真实使用中的导入、选玩家、定位错误和阅读轨迹问题。若简单上传与浏览已足够，可先用轻量本地 UI；需要稳定 API 和定制地图交互时，再考虑 FastAPI + 独立前端。

无论选哪种界面，都应调用同一应用接口；长任务放到 worker，刷新页面不重复提交。当前尚未实现这些服务，也不把框架选择写成已决定事项。

## 3. 为下一阶段模型预留的决定

首个实验建议缩小到同补丁、同角色、一个英雄范围，并分别定义两个任务：

- **出装行为**：在明确决策时刻，用历史状态预测下一候选装备/无事件；处理配方、重复购买、观察不足和动作词表。
- **路线行为**：在固定时间窗内预测下一语义区域或区域序列；先定义地图区域、存活状态及可用上下文。原始坐标本身还不是路线标签。

两个任务可以共享历史状态编码器，先分别训练和评估，再决定是否共享模型。当前没有足够证据选择 Transformer、RNN 或图网络；先做频率/规则基线、小型 MLP/时序基线，并用独立比赛验证复杂模型是否带来收益。

职业选手的行为可作为模仿学习样本，但“选择相似”不能推出“决策正确”。复盘输出至少区分行为偏好、数据适用范围和未知上下文。用胜负或未来收益训练价值模型还涉及队友行为、资源条件与选择偏差，需要独立设计评估，不能把模型分数直接标成胜率。

训练侧的最低要求：

- 特征只来自 cutoff 及之前；未来行动仅用于标签；全知回放字段不能假装玩家当时可知。
- 预处理/词表/缺失填补只在 train 拟合；validation 选方案，test 留到最终评估。
- 保持比赛级隔离，增加更晚时间的留出集；按比赛而非窗口计算不确定性。
- 保存 feature_schema、代码、环境、数据集 ID、超参数、指标计算方法和错误案例。
- 先实现离线评估，再接入个人比赛；必要时让模型明确不输出建议。

## 4. 阶段依赖与范围

```text
已完成：可执行的数据/任务/报告协议
  → 真实语义验收 + 质量/追踪/恢复补齐
  → 截止时间特征、标签与预处理（v0.4 已实现初版，待真实核验）
  → 基线与自己的深度学习模型（下一阶段）
  → 独立评估与可用复盘
  → 按需求扩展 UI、范围或多人服务
```

参考分布和最近邻可作为可解释基线，但不再把“先做完整统计产品/检索产品”设为自建模型的硬依赖。LLM 可在结果可靠后辅助解释，不替代用户计划自行训练的决策模型。
