## 2. 顺序与每一步的交付

| 顺序 | 对应任务 | 工作 | 交付及出口 |
|---|---|---|---|
| A 报告评审 | M03/M04 | 逐条审查现有报告中的需求、装备、理由、条件、代价及缺失项 | 每条问题指向输入/规则/事实；区分机制错误、策略争议、表达误导、证据不足，不先调分掩盖问题 |
| B 机制补齐 | M02 | 核对控制、驱散、免疫、物品可使用性及例外 | 每个生效交互有版本依据和正反例；未知或冲突项不生效，黑皇杖/蝴蝶不直接解除暂缓 |
| C 开发修正 | M03/M04 | 在开发案例上修知识、策略或表述 | 保存版本差异及回归结果；不覆盖旧知识包或历史验收记录 |
| D 冻结评估 | M06准备 | 冻结范围、采样方案、对照基线、评分表、门槛与实现身份 | 在查看最终集输出或评分前记录时间、清单及SHA-256；此时才建立未用于调参的最终集 |
| E 独立验证 | M06 | 对固定版本一次性运行最终集，隐藏方案身份进行评审 | 报告全部案例、各项分母、未知/拒绝比例、错误和与基线比较；未达标明确失败或缩小范围 |

如果最终集暴露问题并被用于修正，它随即变成开发资料；不得继续把同一集合反复调到通过
后宣称独立达标。新版本需要新的未参与调参集合，旧结果保留。

## 3. 先看哪些具体报告

从仓库根目录运行以下命令即可查看现有实现，不需要新建UI或导入回放：

```bash
python recommend.py examples/recommendation/baseline.json --format text
python recommend.py examples/recommendation/no-evasion.json --format text
python recommend.py examples/recommendation/illusions.json --format text
python recommend.py examples/recommendation/unknown-hero-knowledge.json --format text
```

| 报告/对照 | 具体评审问题（不是预设正确答案） |
|---|---|
| baseline | 幻影斧与沉默的关联是否把条件说清？金箍棒/冰眼列为针对方向是否有充足需求依据？是否遗漏更重要的生存限制？ |
| baseline → no-evasion | 移除本包闪避事实后，命中装备与理由变化是否合理？是否把“未收录其他威胁”误当作“没有其他威胁”？ |
| baseline → illusions | 多目标需求改变狂战/漩涡的备选优先级，是否有机制依据？是否只是凭未校准权重偏好某件装备？ |
| unknown-hero-knowledge | 出现未覆盖的祈求者时，“部分分析”的局限是否足够醒目？现有候选是否仍容易被误解为完整方案？ |

每条审查记录至少包含：案例ID/输入指纹、代码/知识/规则身份、候选及触发规则、原报告
陈述、引用支持范围、反例或缺失条件、严重度、处理决定、评审者及日期。
“保留”“修改”“暂缓”“待证据”都可成为结论；无理由的“感觉不对”不是已证实机制错误。

## 4. 控制／驱散／免疫核验矩阵

以下为**待核验问题清单**，不在本次文档更新中赋予任何交互通过状态。

| 交互组 | 必须分开核对的问题 | 至少需要的反例 |
|---|---|---|
| 沉默、禁锢、眩晕、变羊、嘲讽、缴械 | 分别限制施法、移动、攻击还是物品？效果来源/升级是否改变规则？ | 不能把控制都当沉默，也不能把禁锢都当眩晕 |
| 基本驱散与强驱散 | 效果能否被某类驱散移除？发生在施加前、持续中还是结束时？ | 不可基本驱散的效果；驱散发生太晚；玩家无法主动使用装备 |
| 剑刃风暴、幻影斧、黑皇杖 | 按7.41f区分免疫、驱散、短暂无敌与魔法抗性，分别查持续时间和前提 | 已有剑刃风暴不意味着无需另一生存手段；幻影斧不等于持续免疫 |
| 控制穿透与伤害 | 免疫是否阻止施加、仅暂停效果或完全无效？伤害能否独立生效？ | 不能从伤害类型直接推导控制是否生效或是否可以驱散 |
| 代表效果 | 狂风、狂战士之吼、裂地尖刺/变羊、冰封禁制先逐项核对 | 对每个“有效应对”的判断保留一个不成立的条件 |
| 闪避与必中（蝴蝶暂缓项） | 普通攻击、概率穿透、特殊攻击以及破坏被动的关系 | 不将概率穿透当作所有攻击必中，不忽略敌方实际装备未知 |

每项保存效果主体、目标、前置条件、升级/等级条件、适用版本、原文或可重现证据、引用
位置与哈希、冲突项及结论。单个官网枚举不得在未核对定义时自行解释。
目前仅有“官网当前补丁＋三个装备改动锚点”的关联，它不是上述交互已通过的证明。
能通过公开资料解决的由开发者查证；确需操作用户电脑/游戏客户端时另行取得同意。

## 5. 不参与调参的案例与对照

- 开发集：现有6个案例，加上报告评审中发现的正反例；可用于修规则。
- 最终集：在开发修正完成、策略冻结后按预先写好的机制分层方案采集/构造。
  记录来源类型（真实公开阵容/合成），两类结果分开汇报，不伪装成职业比赛。
- 去重：用规范化阵容指纹，不能靠交换队内顺序制造新案例；同一真实比赛及其变体归为
  同组。与开发案例高度相似的单英雄替换另列“变体挑战”，不冒充完全独立比赛。
- 分层至少覆盖：相关知识齐全、部分缺失、沉默/驱散条件、不同控制类别、免疫例外、
  队友保护不能保证承担、无合适候选。数量及各层分配在首次运行前冻结，不事后挑好案例。
- 朴素对照：固定一号位主宰的阶段性候选路线，不随对手调整；必须采用相同装备范围、
  输出预算和相同范围声明。先冻结具体条目，不把当前推荐器自己的规则输出当独立标准答案。
- 如做盲评，隐藏策略名称、分数和生成方式，仅保留判断需要的阵容、候选、条件与解释，
  随机排列方案并保存映射。开发者AI自评只能称内部审查，不冒充独立专家或用户认可。

## 6. 评估项、门槛与失败处理

拟采用的评审维度如下；评分表、案例数量和策略优劣的数值门槛在D步骤执行前冻结，
目前没有最终集和已冻结的数值质量结论。

| 维度 | 报告方式 |
|---|---|
| 机制正确性 | 错误数/被审查交互数；严重错误单列，不能用其他建议得分抵消 |
| 引用与条件 | 有足够来源支持且保留必要条件的陈述数/全部被评陈述数；不能只报“引用存在” |
| 建议合理性 | 对英雄职责、阶段、机会成本和替代方案逐项评审；记录分歧和评审者 |
| 覆盖与拒绝 | supported/partial/unsupported各自案例数；未知、暂缓和无候选的原因分布 |
| 相对固定路线 | 成对比较更合理/相当/更差的案例数及理由，不解释为胜率提升 |
| 稳定性 | 无关变化不应改变无关结论；有机制依据的变化应能解释，不能只检查分数变化 |

硬性原则：仍存在已知严重机制错误、把未知当确定、虚构证据或缺失必要条件的建议，
不能宣布其适用范围已验收。若证据不足则缩小范围或保留暂缓，不靠调高总分宣称通过。
整体质量结论需附覆盖范围、全部失败案例及尚未检查的机制；规则版验收不解除真实训练held。
