# 路线B：意识层面决策（防被抓、参团、集合抓人）

状态：**设计草案（2026-11-01）**。方向由用户决定（[U37](decisions/2026-11-01-two-tracks.md)）；下文的拆分、分层、阶段和估时是助手建议，定义类问题（Q14–Q16）须用户拍板后才冻结。进度只看[计划](development-plan-2026-10-30.md)§7；架构见[架构](architecture.md)。

## 1. 为什么这是差异化

| 产品 | 公开描述的相关功能 | 与本项目的重合 |
|---|---|---|
| Dota Plus | 按分路、阵容、已购装备给建议；死亡总结 | 覆盖赛前出装与部分复盘 |
| Dota2ProTracker | 高分段/职业比赛的出装与版本统计 | 与8780出装节奏参照几乎相同 |
| DotaJudge | 对线、补刀、死亡、团战、关键装备时间分析，对比职业样本 | 与赛后复盘目标最接近 |
| DotaMirror | 输入match ID，基于OpenDota与基准生成报告 | 与复盘v0流程相同 |

（以上为用户整理的公开描述，助手没有逐项核实这些产品的当前功能。）

路线A的产出与这些产品高度重合，样本和覆盖面也比不过。路线B想做的不同之处：

1. **只用当时可知的信息评价决策**：按阵营还原视野和信息年龄，并考虑查看成本（U6）；不拿全知数据或结局倒推“你当时该知道”。
2. **区分风险/结果和高分段行为**：两种模型并列，方向相反时不出建议；行为不等于最优。
3. **机制依据可追溯**：敌方抓人能力、逃生手段、技能就绪由MK规则推出，附官方原文出处。
4. **证据不足就写“未知”**。

## 2. 三类判断

| 判断 | 每一刻回答什么 | 客观标签 | 难度 | 建议顺序 |
|---|---|---|---|---|
| 防被抓 | 当前位置和状态，接下来20–30秒被围的风险 | 能自动生成：之后是否死亡、是否被≥2名敌方英雄接近 | 低 | 1 |
| 是否参团 | 队友要打或已开打时，去、继续刷还是晚点去 | 部分：去/不去之后90秒的人头、经济差、目标得失 | 中 | 2 |
| 集合抓人 | 有没有能抓的目标，能否及时凑够人 | 难：协同、反事实、开雾不可见 | 高 | 3 |

20–30秒、90秒等窗口是助手的举例，待Q15确定。

## 3. 四层设计

1. **可知性层（输入）**：敌方最后可见位置与年龄、己方眼位（时刻存活待认证）、可见敌方装备、队友状态；查看成本按规则近似（如信息年龄超过X秒视为未知）。
2. **事实/计算层（不用ML）**：TP冷却、合法落点、步行时间与到场时间、关键技能就绪；敌方抓人能力由MK推导。
3. **模型层**：风险/结果模型（给定可见状态，之后会发生什么）＋行为模型（高分段在类似状态下怎么做）；两者矛盾时拒答。
4. **呈现层**：时间点 → 当时可见证据 → 风险/结果 → 高分段做法 → 建议 → 置信度与适用条件。

## 4. 阶段（计划中的B0–B5）

| 阶段 | 内容 | 出口 | 主要风险 |
|---|---|---|---|
| B0 定义冻结 | 触发点、标签、时间窗口、可见输入清单；用户确认后冻结 | 任务契约与决策记录 | 冻结后不能为结果改定义 |
| B1 数据试点与扩容 | 先试点20–30场（含用户本人比赛），实测下载成功率、解析失败率与耗时、关键字段可修复性；再定300–500场规模 | 字段准入报告、冻结快照 | 联网授权；大文件；解析耗时 |
| B2 防被抓v1 | 规则基线→逻辑回归→sklearn梯度提升（不加依赖）；按比赛划分；校准；MK解释 | 模型卡；用户比赛上抽查高风险时刻 | 开雾只能看到效果；反应混杂 |
| B3 参团v1 | 到场时间直接计算；相似状态下去/不去的结果匹配对比；高分段行为参照 | 正式复盘页；用户评审 | 混杂：只能写相关 |
| B4 集合抓人v1 | 机会识别（孤立、逃生手段冷却、我方在附近）＋尝试后成功率 | 机会清单与成功率参照 | 样本少，多数情况可能拒答 |
| B5 复盘整合与独立评估 | 并入复盘报告；另取评估集只测一次 | 评估报告；用户用3场比赛试用 | 如实记录 |

## 5. 数据工程难点

| 难点 | 现状 | 应对 |
|---|---|---|
| 可知性重建（最核心） | 已有阵营时间线与最后可见年龄；眼位时刻存活、开雾效果时段、同tick顺序未认证；整段团战汇总含未来信息已排除 | 认证前标“未知”；查看成本按规则近似 |
| 字段语义认证 | 蓝量范围65536→8192问题未修旧数据/生产者；TP/技能冷却未导出；持有≠可用；兵线野区存量未导出 | 逐字段核对读取函数、单位、实体，抽查画面 |
| 录像获取 | 下载链接会过期；单场几十到上百MB；云端无`data/`；两场大文件需专门恢复 | 冻结窗口内采集，预算/回执/断点恢复（复用采集脚本机制） |
| 解析器兼容 | 10/22试点Gem 0.10.0三场提前终止，后修到13场 | 每个补丁窗口重新验证；记录解析器谱系 |
| 时间对齐 | 用哈希一致的GameClock，不用tick/30 | 事件严格早于决策时刻 |
| 事件/决策点抽取 | 每场7–8万条战斗日志 | 团战/抓人/支援的归纳本身需要定义和验证；处理截断与反应混杂 |
| 地图几何 | 只有494个建筑地标与底图，无寻路网格 | 到场时间按可走路线，不用直线距离 |
| 规模与独立性 | 样本单位是比赛而不是秒 | 按比赛划分，控制段位与补丁窗口 |
| 可重现治理 | 冻结、哈希、不覆盖、迁移登记 | 规模越大开销越明显，需要提前规划 |
