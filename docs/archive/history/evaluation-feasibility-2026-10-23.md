## 5. HTTP 400的具体诊断

保存文件：`data/purchase-until-daily-2026-10-22-proxy-resume-01/batch-0001/discovery.json`。

```json
{"status":400,"body":"{\"err\":\"Error: Query read timeout\"}"}
```

查询为OpenDota `/api/explorer`，游标`match_id<9056002383`，原日期/英雄/模式/段位筛选未变。
将SQL中match_id游标数值替换为同一占位符后，**5页此前成功发现请求与失败查询模板相同**。这支持该查询结构此前可执行，但不证明当前服务正常或失败必然短暂。

现有采集器先保存响应正文，再raise_for_status并停止，未发现其因400无限重试或绕过预算的问题；本轮不为追求继续采集而放松它。

后续复测建议（未执行）：

1. 冻结小预算和完整请求列表，最多5次；沿用原预算/出口，匿名，不付费parse。
2. 先测试1次原失败发现查询；若再次400/429立即停止，不在本轮循环重试。
3. 成功后才进行受控的小范围查询/详情连通性检查；测试样本单独登记，不自动加入正式评估。
4. 若持续超时，再设计保持资格不变的时间分片/游标策略；变更发现覆盖和排序必须有离线测试与新协议，不能根据装备或胜负缩小查询。

小预算复测只判断当前路径，不保证能采到目标N。缩短查询窗口可能减轻负载只是待验证假设，不能宣称已修复服务端性能。

## 6. 200/500/1000场精度与成本情景

只读取旧398场validation已保存的frequency与C=0.1预测，分别核对complete哈希、成员集合、标签/mask、来源哈希和split一致；不调用训练或新数据预测。
旧398场11装备mask全有效，因此对每场取11装备成对平方误差差值的均值，与固定11项宏Brier差完全对应：

- mean(d)=-0.0031088064；样本标准差s=0.0221249989。
- 用`1.96*s/sqrt(N)`作**IID正态近似规划半宽**，不是新样本实测区间，也不是统计功效计算。

|合格比赛N|IID近似95%半宽|假设仍只有5.4%详情通过，所需详情数约|
|---|---:|---:|
|200|0.00307|3,704|
|500|0.00194|9,260|
|1000|0.00137|18,519|

请求数尚未包含发现请求、网络失败、重复及未来资格损失；5.4%来自本次非随机两小时队列，不是稳定成功率预测。
若有效设计效应为2或4（仅情景，不是已估计值），半宽分别乘sqrt(2)或2，达到相同精度需要约2或4倍比赛数。

仅按旧IID方差，半宽≤0.005公式得到N=76，但**不建议据此定为76场即可**：该半宽大于旧收益0.0031；同时忽略旧验证参与选模、玩家依赖、时间和补丁迁移及逐装备稀有支持。200场的近似半宽也已接近原收益，不能保证检出。

据此建议：把200场定位为可行性/探索性预算档，500场作为较充分主比较的待确认预算档；先解决覆盖与日志可用率，再决定能否承担请求成本。1000场不能仅因更多就默认采集。现阶段不冻结N，不承诺统计显著，不改变已写停止规则。
