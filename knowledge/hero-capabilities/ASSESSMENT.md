# 选人阶段能力评估定义

## 输入与输出

当前学习基线：用户明确选择先学习当前官网版本，再补历史版本。默认使用已保存的当前官网快照，不要求先完成 7.41f 适配；官网未明确标注的具体版本号仍保留未知。

输入：当前资料快照、双方各五个英雄；已知命石或其他选人信息可附加，没有则保留未知。未来进行历史分析时再显式指定对应版本。

输出：双方的能力来源、限制、可能的组合条件、待确认的功能缺口和需要在比赛中继续观察的事项。不是胜率、装备列表或总战力。

英雄被选中只证明有其能力体系的潜力，不代表技能已学、魔法足够、冷却完成、目标可见、已购买升级，或配合一定成功。

## 四层结构

1. **技能事实**：官方描述、目标、范围、施法与冷却数组、注意事项、升级条件。
2. **机制解释**：伤害／控制／机动／防护等具体能力；需要逐条核对作用对象、条件、例外。
3. **阵容组合**：谁提供哪种能力，组合是否需要命中、先手、站位、树木、等级或升级；不能把五名英雄的标签相加当成强度。
4. **装备需求**：在实际等级、装备、视野、经济和地图状态下，判断需要补什么功能。本次不自动跨到此层。

## 核心测评范围

| 能力组 | 必须解构的内容 | 不能自动推导的结论 |
|---|---|---|
| 控制 | 眩晕、缠绕、沉默、禁用物品、缴械、减速、强制位移、区域限制；区分不同控制 | 有控制就能打断所有动作、控制必中、减益免疫一定有效或无效 |
| 伤害 | 来源与类型、攻击／技能、单体／范围、爆发／持续、生命值等条件性缩放 | 有范围技能就能快速清线、有分裂就一定克制幻象、伤害量足够 |
| 机动 | 自身／队友／敌方位移，追击与撤退条件，距离、路径、充能、目标限制 | 位移一定能逃生、临时位置变化等于永久位移 |
| 防护与恢复 | 治疗、护盾、伤害吸收、驱散、救援、无法攻击／被攻击等；同时记录代价 | 有恢复就能抗住爆发、隐身就是无敌、所有控制都能被驱散 |
| 信息 | 视野、隐身、揭示等具体机制，以及目标方向和持续条件 | 隐身即无视侦测、提供视野就提供真实视域 |
| 资源与目标 | 清线、野区、建筑作用、召唤物；依赖等级、经济和环境的程度 | 角色标签 Pusher 就代表当局能安全拆塔，野区标签证明当前打法 |
| 队伍功能 | 先手、反先手、保护、追击、持续交战、爆发窗口、资源分工 | 有相同标签就必然冗余，英雄名字决定当局位置 |
| 成长与条件 | 等级、天赋、命石、神杖／魔晶、技能组合、冷却、资源需求 | 自动拥有完整技能集、默认所有升级，阵容能力全时段固定 |

以上是需要解构的范围，不代表官网字段已经完整证明所有能力。注册表的 22 个检索维度只是定位相关技能文本的工具；目标方向、可靠性、连招关系等还需核验。

## 一条能力记录应包含什么？

```text
英雄和技能
→ 具体机制（缠绕≠眩晕，沉默≠禁用物品）
→ 作用对象（自身、队友、敌人、区域）
→ 触发与命中条件
→ 是否需要等级、天赋、命石或升级
→ 关键限制和代价
→ 来源、版本与核验状态
```

不能由技能文本中的一个词自动判定方向。例如出现 healing，可能是治疗友军，也可能是阻止敌方治疗；描述出现 invisible，也可能是“不能命中隐身单位”。本次自动检索结果统一为待核验线索，绝不转成已确认能力。

## 选人阶段可以怎样表达判断？

采用条件句：

> 已选英雄 A 的技能 S 有某种机制；在条件 C 满足时，可提供功能 F。还需确认 X。当前不能据此认定结果 R。

未来讨论组合时，每个组合判断必须分别引用双方相关技能，并写出接续条件。反制关系不能凭英雄名字生成；机制存在也不等于克制强度已经验证。

## 状态与准入

- `official_source_fact`：官方快照明确写出的说明或数值，仍受版本限制。
- `text_signal_needs_review`：检索线索，可能是限制或否定，不能作为机制事实。
- `agent_source_checked_patch_unverified_user_review_pending`：已逐条对照来源的解释示例，仍未确认目标版本，也未成为共同认可的战术规则。
- `unknown`：缺资料或尚未核对；绝不能记作不存在。

版本适配、资料核对与训练准入是不同环节。本目录不改变原有 held 状态，也不将来源通过解释成决策质量监督可用。
